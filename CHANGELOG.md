# Changelog

Newest first, grouped by date. **The entry lands in the same commit as the change** — that is
the whole discipline, and why this file replaced `process/toolkit-worklog.md` (which rotted the
moment updating it became a separate chore). One line per change:
`kind(area): what and why (field evidence / bug id) — contributor or source project`.
Kinds: `new` · `fix` · `learn` (a skill/learning) · `process` (rules, templates, CI).
Credit the person or project that surfaced the change — the credit line is the thank-you.

## 2026-09-01
- fix(obligation-check): the obligation checker read the **oldest** matching artifact, so a pass that was performed again — properly — could not clear its own finding. `_ob_find`'s `match=names` branch returned the first glob hit, and glob order is alphabetical, which for the `ui-review-<YYYY-MM-DD>*.html` schema means oldest first. A migration re-reviewed its module with five pages, five `PROOF-OF-LOOK:` citations and five committed captures, and `gate-check.sh` still printed `Obligation look FAULT — 0 of 1 discharged; NO PROOF-OF-LOOK`, because a superseded report from the previous day was the only file ever opened. **That is the worst shape a guard can take: the remedy it names does not clear it**, so the author adds more proof, watches nothing change, and learns the check is broken. `_ob_find` now returns **every** match newest-first and the consumer walks them, taking the first that satisfies all three disqualifiers (denominator, LOOK proof, staleness) — which also makes tie order harmless, since a tie no longer discards anyone. An older report can still only win if `_ob_stale` clears it, i.e. the model has not been built past it, so nothing is gamed by keeping old reports around — a dashboard-publishing migration project
- new(tests): `tests/retests/retest-obligation-newest-report.sh` — seven assertions over `_ob_find` (newest date beats a newer mtime, same-date pairs are both offered, ordering is deterministic, dateless falls back to mtime, the unit filter beats recency, empty files are skipped, `match=path` is untouched). Written after the first attempt at this fix shipped a call to `_ob_mtime`, **a function that does not exist** — masked by its own `2>/dev/null || echo 0`, so every file tied at 0 and only the date in the filename was really sorting. A green run over a fixture I hand-built would have said PASS; what caught it was grepping for the callee. The second attempt then sorted on sub-second mtime, which this container's ext filesystem stamps identically for files written milliseconds apart — the reason the fix above stopped trying to resolve ties at all — a dashboard-publishing migration project
- fix(tests): `retest-bug22-settings-writes.sh` resolved the java symlink with `readlink -f`, which is GNU-only and absent on macOS — caught by `check-portability.sh`, which CI runs on every PR, in the toolkit's own test tree. Replaced with a bounded symlink walk, verified to produce byte-identical output to `readlink -f` on a real two-hop `/usr/bin/java` — a dashboard-publishing migration project
- fix(mdl-preflight): **STOP rule 2 is retired** — `alter project security level`, `alter settings configuration` and `alter settings model` do NOT corrupt the Settings unit on mxcli v0.20.0 / Mendix 11.12.1, and every project has been sent to the Studio Pro GUI for a statement mxcli implements correctly. The rule dates from v0.13.0 / 11.12.0 Beta (BUG-22) and the toolkit's own consolidated log flagged it as possibly stale on 2026-08-06 — item 4, `BUG-LOCAL-05` passing on both forks — and nobody reconciled it for a month. Falsified with the bug report's OWN stated detector: it says the model fails to load "on the next SP open **or `mx check`**", and `mx check` runs headlessly. **18 executions, 0 errors on every one** — six level toggles through all three levels, both sibling statements, ten consecutive toggles on a model carrying 23 scripts of content, and a full `mxbuild --target=deploy` (BUILD SUCCEEDED), with the written values asserted to round-trip because a clean check over a lost write is not a pass. Honest limit: no Studio Pro in a Linux container, so the SP-open path is not independently exercised. Reported by the user of a dashboard-publishing migration, who was right — a dashboard-publishing migration project
- new(tests): `tests/retests/retest-bug22-settings-writes.sh` — the retest above, committed and re-runnable (`<mxcli> [content.mpr]`), so the next person confirms or reopens the rule in a minute instead of re-flagging it in a year. **The generalisable ask: every STOP row should name the command that would falsify it.** A "may already be fixed, unreconciled" note is a claim with no owner — too weak to change behaviour, too strong to ignore, so it survives — a dashboard-publishing migration project
