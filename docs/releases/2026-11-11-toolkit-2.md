# Toolkit 2

Toolkit 2 builds a Mendix app faster, and it proves more of what it built. It can report toolkit
bugs for you, with names and paths redacted. Existing projects change in a few places after sync;
see "What behaves differently".

"Toolkit 2" is a name for this batch of work, not a 2.0 milestone and not a version: the cut is an
ordinary dated release, tagged `v2026.11.11`, and there is no migration step beyond pull and sync
(see "How to upgrade"). How releases and milestones relate:
[`docs/RELEASE-PROCESS.md`](../RELEASE-PROCESS.md) §6 and §8. Every line below traces to an entry in
[`CHANGELOG.md`](../../CHANGELOG.md). The speed figures come from one run on one app each.

## What's new

1. **Pipeline modes.** Choose speed or rigour per project. `balanced` is the default;
   `high-speed` skips the per-row page check; `high-quality` keeps the earlier per-row journeys
   and checks. Put `Pipeline mode: high-quality` in `PROJECT.md` to keep the old cadence. In the
   mode experiment, balanced took 3.25 min per row against 4.65 for high-quality (net of module
   close), high-speed 2.05, and no mode missed a defect.
2. **Speed core.** Re-runnability is proven by one `mxcli diff` (1.7 s) instead of a second gated
   exec (35 to 120 s). A hung journey is cut off after 120 s and named, instead of sitting for
   minutes.
3. **Cheaper builds and tests.** Each exec runs the lighter `mx check`; the full build runs at
   module close and before a push. `bin/doctor.sh --bench` times your machine.
4. **Persona preflight.** A journey batch that logs in as a user who does not exist now fails
   before it starts, with one line per persona (the check reads demo users in about 1 s), instead
   of each journey waiting about 100 s for the login.
5. **Bug reports that file themselves.** See "Report a bug".
6. **More honest gates.** Stage 2 no longer trusts a requirements-driven BRD that calls itself
   "Clean"; Stage 3 fails an interaction model that leaves out a user task; a confirmed
   Marketplace "Buy" is checked against the model before the build; Stage 0 no longer passes a
   `_pending_` sign-off. Six gate false greens and reds from a field run are fixed.
7. **Journeys do more.** They can press Back, run as a phone, go offline and online, set a GPS
   fix, and click a named grid row.
8. **Better unit tests.** Tests pick inputs from each flow's decisions (blank strings,
   boundaries, every enum value) and read a committed row back from outside the test.
   `project-bin/rollback-scan.sh` lists side effects that a rollback will not undo (REST calls,
   files, queues and similar). It is advisory.
9. **Testing flaky networks and timers.** `project-tests/e2e/link-proxy.js` simulates latency,
   bandwidth limits, loss, a service that is down, lost requests or replies, and refusals in
   front of a service; `exactly-once.js` flags a redelivered request. The unhappy-path guide gains
   a "Timed windows" section for timer-driven flows. `project-bin/project-facts.sh` prints ports,
   roles and secret key names (never values).
10. **Workflow and mxcli learnings.** A workflow-called microflow returns nothing by default (new
    STOP row 34). Also: find constant usages with `search`, not `SHOW REFERENCES TO`; a queued
    call with a retry policy blocks rewriting its microflow; use `--skip-app-startup` when
    `mxcli test --local` hangs.
11. **Multi-app systems.** `bin/contract-check.sh` compares published and consumed service
    contracts across the apps of one system. It has not yet been run on a real multi-app system.

## Settings you can change

| Setting | Where | Effect |
|---|---|---|
| `Pipeline mode: high-speed`, `balanced` or `high-quality` | `PROJECT.md` | What runs per build row and what waits for module close. No line means `balanced` |
| `UI polish: <N>% / <R> rounds` | `PROJECT.md` | Overrides the polish loop's stop point at module close |
| `Gate mode: full` | `PROJECT.md` (or `MXTK_GATE_MODE=full`) | Keeps a full build per exec instead of the `mx check` default |
| `JOURNEY_TIMEOUT_S` | environment | Journey time limit, default 120; `0` removes it |
| `Bug filing: auto` | `PROJECT.md`, committed | Lets `bin/file-bugs.sh --auto` file clean reports with your own `gh` login |
| `MXTK_BUG_EMAIL` | `.claude/toolkit.env` or `~/.mxcli-toolkit.env` | Address printed on a bug bundle |

Settings from earlier releases: [1.0 notes, section 2](v1.0.md#2-settings-you-control).

## What behaves differently

After `sync-project.sh`, an existing project will notice:

- **Cadence.** With no `Pipeline mode:` line the project is `balanced`: no journeys per row, unit
  tests and the full pre-push build at module close. sync prints one line when the line is missing.
- **Section-wide coverage claims now FAIL.** A plan row such as `F001/microflows/* (5)` claims a
  whole section at once. It FAILs Stage 4 and the coverage step of `verify-module.sh`, so a
  mid-build module can go red after sync. Remedy: split the claim per element, or record
  `Waived artifact coverage-ledger: <reason>`.
- **Modules with no real journeys run now read PENDING.** The journeys check used to count the
  summary file existing; now only a journeys row of PASS or FINDING counts. A module whose runtime
  was down or whose journeys were skipped flips from done to PENDING.
- **Stage 1 reads extraction-quality files.** A file below threshold, with missing dimensions, or
  unparseable FAILs. With no file, the PASS line says quality was not scored. A triage naming auto
  mode as confirmer is a FAIL unless `Interview mode: auto`.
- **Untouched scaffolds read PENDING, not FAIL.** This covers a triage scaffold, a missing
  sufficiency rubric and sources with no inventory.
- **Journey timeout.** Each journey stops after 120 s: a named FAIL ("journey TIMEOUT"), the rest
  INVALID, exit code 124. `JOURNEY_TIMEOUT_S=0` removes the limit.
- **Persona preflight can stop a module close.** A missing persona or role records a FAULT and the
  journeys do not start.
- **Idempotence check.** `idempotence-check.sh` exits 1 on a script that cannot be re-run, 2 when
  it cannot tell. For stubs and `alter page insert`, which are refused on re-run by design, the
  result is informational.
- **Exit codes.** `exec.sh` returns 4 for "applied, gate passed, lint only" and 5 for "applied,
  unverified"; wrappers that test for 1 must be updated. `monkey.js` and `named-controls.js`
  return 2 for "not measured" (a FAULT row).
- **Stricter gates.** New FAILs at Stage 0 (`_pending_` sign-off), Stage 2 (false "Clean"), Stage 3
  (interaction model gaps) and build-ready (a confirmed Buy not installed).
- **Bug filing.** `--auto` without a usable `gh` writes a bundle, not links, unless you declare a
  GitHub account.
- **Loosening a baseline** (lint or conformance) needs you to type `loosen` in your own terminal.
- **Check-only build gate** is the default; `Gate mode: full` opts out.

## How to upgrade

```bash
git -C ~/Mendix/mxcli-project-toolkit pull
~/Mendix/mxcli-project-toolkit/bin/sync-project.sh <project-root>
```

sync prints your `Toolkit release:`. To stay on a release, `git checkout <tag>`.

## Report a bug

Log a bug once with `bin/file-bugs.sh --add`. Everything is redacted first (home paths, user and
host names, emails, IPs, tokens, project, module and entity names, and your deny list); a report
that still looks unsafe is held back. Then pick the path that fits:

- **Automatic (opt in).** Add `Bug filing: auto` to `PROJECT.md` and commit it.
  `bin/file-bugs.sh --auto` then files every clean report to GitHub with your own `gh` login,
  after a duplicate search.
- **Free GitHub account, no install:** `--links` prints a pre-filled link per bug.
- **No GitHub:** `--bundle` writes `toolkit-bugs-<date>.md`. Mail it to the address on its first
  line (`MXTK_BUG_EMAIL`, set by whoever gave you the toolkit); the maintainer files it with
  `--import`.

## Known limits

- Not yet run on Windows/Git Bash: pipeline modes, the journey timeout, persona preflight, bug
  filing, link-proxy, project-facts and rollback-scan. Their measurements are from Linux.
- Speed figures come from one run on one app each.
- `contract-check.sh` has not been run on a real multi-app system.
- The Marketplace "Buy" check has not been run against a real build with a Marketplace install.
