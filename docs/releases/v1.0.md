# mxcli-project-toolkit 1.0

**What it is.** A shared process layer for building and changing Mendix apps with an AI coding
agent and [mxcli](https://github.com/mendixlabs/mxcli). It gives the agent a staged pipeline
with recorded decisions (`PROJECT.md`), skills it loads only when a task calls for them, and
mechanical gates (`bin/gate-check.sh`, lint, mxbuild, end-to-end journeys) that report what is
actually in your project. It runs for migrations, requirements-driven builds, greenfield builds
and changes to a live app, or a la carte to audit and test an app you already have.

1.0 is the first named milestone on top of the release train, and the first tag published to
GitHub (`v1.0`). Earlier dated headings in the CHANGELOG were never pushed as tags. All v1.0
work merged into the `release/v1.0` branch while master stayed frozen; the tag marks that
branch. Every PR named below has merged, some through the integration batch
[#329](https://github.com/MendixMau/mxcli-project-toolkit/pull/329). Every line traces to an entry in
[`CHANGELOG.md`](../../CHANGELOG.md) or to a linked PR. How milestones relate to tags:
[`docs/RELEASE-PROCESS.md`](../RELEASE-PROCESS.md) §8.

## 1. Performance improvements

### Testing at key moments

A twenty-task UX-fix retro measured what testing every change costs
([#274](https://github.com/MendixMau/mxcli-project-toolkit/issues/274)): UI-only changes were
re-proven 5 to 10 times (their own journey, the regression journeys of 4 to 5 other modules,
reviewer re-runs), a full `mxcli test` took about 6 minutes at every batch close, and 143 minutes
of unit tests found stale strings and credential problems, not logic bugs. 
The toolkit now runs tests at fixed moments and keeps a change small. Per change, the build gate
plus what the change touched. The full run happens once when the build is complete and once
before every later deploy. Unit tests are off by default and switched on only where logic needs them
([#290](https://github.com/MendixMau/mxcli-project-toolkit/pull/290),
[#417](https://github.com/MendixMau/mxcli-project-toolkit/pull/417)). They are chosen per flow: a module brief lists the
`Unit flows:` worth a test, one line each with a reason, and `affected-tests.sh` runs only the
listed flows a change touched. That follows the maintainer's policy that unit-testing everything
is overkill: logic and integrations get unit tests, and UI journeys catch the rest
([#435](https://github.com/MendixMau/mxcli-project-toolkit/pull/435), [#436](https://github.com/MendixMau/mxcli-project-toolkit/pull/436)).

| Moment | What runs |
|---|---|
| Every change (build and feedback) | The gate, plus what the change touched |
| Module done | That module's journeys |
| Build complete | Everything, once |
| Before every later deploy | Everything, once again |
| You ask | Everything |

"What the change touched" comes from the script itself: `./bin/affected-tests.sh <script.mdl>` lists
the unit tests and journeys a change owes, from the elements the script writes and the flows
that call them
([#416](https://github.com/MendixMau/mxcli-project-toolkit/pull/416)). On three real change
scripts in a five-app project it selected 0 to 1 of 20 journey files and 0 to 1 unit test files
per change. It is advisory and exits 0. It also reports `journeys unmapped N of M` for journey
files that name-based selection cannot reach (12 of the 20 held no qualified name), so an empty
selection is never read as "nothing owed". `exec.sh` prints the `affected tests:` hint on every
MDL run. The first call takes about 19 seconds (it builds the mxcli catalog), later calls about 3
seconds.

### Other speed items

- **Where an exec spends its time.** The run summary and `docs/BUILD-LOG.md` now carry per-step
  seconds (`steps: guards Ns check Ns snapshot Ns baseline Ns exec Ns gate Ns lint Ns score Ns`),
  and a run whose gate fails keeps its gate seconds. Those failed or rolled-back runs were 47 of
  238 rows in the measured project and its costliest 20%. The timing costs about 0.2 seconds per
  exec, 0.5 to 0.7% of a 28 to 41 second exec
  ([#413](https://github.com/MendixMau/mxcli-project-toolkit/pull/413)).
- **Fewer build rows.** A `BUILD` row is now one use case, and a script is the rollback unit.
  Two Stage 4 runs on the same requirements had produced 137 and 246 rows (2.5 rows per use
  case); build cost followed the row count, 11 versus 25 model calls per row and about 11 versus
  about 40 hours. A Stage 4 A/B on two fixture modules (22 use cases) gave 1.05 rows per use case
  with the new text and 2.27 to 2.45 with the old.
- **Stage 5 drafts in parallel.** Every build-plan row whose dependencies are applied, minus rows
  that write the same document, is drafted at once, one helper per script. Applies stay one at a
  time through `bin/exec.sh`, and the ready set is recomputed after each
  ([#343](https://github.com/MendixMau/mxcli-project-toolkit/pull/343)).
- **Less to read at the start.** The always-loaded skill tier went from 79,997 to 76,259 words
  with no rule removed
  ([#315](https://github.com/MendixMau/mxcli-project-toolkit/pull/315)). A helper reads only the
  baseline rows for its own role. The mdl helper at Stage 5 went from 56,236 to 43,599 words
  (the runbook slice for its stage) and then to 30,647 (a routing row on demand for one role).
  Routing tables are trigger lists, so a session no longer re-reads the whole runbook (about 24k
  tokens) on every later call.
- **The app map refreshes only what changed.** On a 17,500-unit app the loop sweep re-described
  every loop-containing microflow: 1,917 describes in 2 hours 45 minutes at 6 workers, while about
  80 units had changed between rounds. It now describes only changed units. On a synthetic
  2,000-unit app with 1% changed that is 20 describes instead of 2,000, and `bin/status.sh` shows
  how stale the map is. No field run of the incremental sweep yet.
- **Context packs** cut helper tool calls and time; see section 3.

## 2. You manage your own testing

These are the settings a project owner controls: what runs and when, how much the agent
asks, and what it is allowed to touch. They survive `git pull` and `bin/sync-project.sh`.

| What you want | The line or command | Where it lives |
|---|---|---|
| Unit tests across the project | `Unit tests default: no` (the default) or `yes` | `PROJECT.md`, intake Q13 |
| Unit tests for one module | Set the Unit row of the module brief's Test plan to `yes` and name why: `\| Unit (.test.mdl) \| yes \| <the calculation, mapping, Java or REST logic, or the fixed bug> \|` | `architecture/modules/<Module>/module-brief.md`, `skills/module-brief.md` |
| What runs at each moment | `## Test strategy` table, offered at CAC-5 (architecture and offer, before the build). Status `CONFIRMED`, or `ASSUMED` in auto mode. Change any cell in your answer to the offer | `PROJECT.md`, `checkpoint-build.md` |
| Everything, now | Say "run everything". The full suite runs once on request | in chat |
| Which flows get a unit test | List them in the module brief as `Unit flows:`, one `- ACT_X: reason` line each. A list wins for its module even under `Unit tests default: yes` | `architecture/modules/<Module>/module-brief.md` |
| Per-change test selection depth | `./bin/affected-tests.sh <script> --depth N`, or `MXTK_AFFECTED_DEPTH` (default 1) | shell |
| Context packs | `Context packs: on` (default), `no-brain` or `off`; `MXTK_CONTEXT_PACKS` for one command | `PROJECT.md` |
| Ask before each exec | `bin/exec-approval.sh <project> --set auto` (default) or `--set ask`; `--clear` removes it | `.mxtk/exec-approval`, or `Exec approval:` in `PROJECT.md` |
| Fewer or more questions | `bin/interview-mode.sh <project> --set steering\|assist\|auto` | `Interview mode:` in `PROJECT.md` |
| Keep sync from restoring the look-ledger hook | Create the file `.mxtk/no-hook-repair` | project root |
| Check staged files for real secret values | `bin/check-staged-secrets.sh` (staged blobs) or `--tree` (everything tracked). Opt-in; not part of the pre-commit hook | project |
| Install only some scripts on sync | `bin/sync-project.sh <project> --only-bin <script.sh>` | toolkit clone |
| Commit before an exec that needs a clean model | `bin/exec.sh --commit-first` | shell |
| Longer verify-module rungs on a big app | `VM_TMO_GRAPH`, `VM_TMO_COVERAGE`, `VM_TMO_JOURNEYS` (defaults 300, 300, 900 seconds) | shell |
| A lint rule off | `enabled: false` under `rules:` in `.claude/lint-config.yaml`, recorded in `PROJECT.md` | project |

The test strategy and the unit default are two settings. The strategy says when a test set runs.
The unit default says whether unit tests exist in that set. `affected` selects from the tests
that exist and does not ask for new ones.

## 3. Context packs

A helper that builds one step of a module used to get a reading list. With context packs it gets
one file ([#198](https://github.com/MendixMau/mxcli-project-toolkit/pull/198)). The module brief has a `### Build steps` table, one row per dispatch: what the step
builds, which existing elements it reads, the app's own example to copy, and the `mxcli brain`
slice. `bin/context-pack.sh <Module> <Step>` turns that row into a pack made of the folder from
the brief's folder plan, the why from `mxcli brain brief`, the brief's architecture constraints,
and a live `DESCRIBE` of every element the step reads, of the example, and of anything it
changes. The pack also lists the rule files the step must read, the attributes a `TEXTBOX`
cannot bind on a page step (mxcli `check` passes them, `mx check` fails with CE2421), and the
`mxcli impact` list when the step changes an existing element. The pack is regenerated per
dispatch and never committed.

**Why it helps, as measured.** On a real app's scratch copy, 3 helper runs with a pack against 3
without, same brief and brain: about 9% fewer tokens (130k against 144k), about 40% fewer tool
calls (13 against 21) and about 40% less time (60 seconds against 101). Every run passed
`mxcli check` and executed with no new mx errors. Page steps with the later pack used about 25%
fewer tool calls and about 30% less time (n=2 each, too few runs to quote tokens).

**The switch.** `Context packs: on | no-brain | off` in `PROJECT.md`, default `on`.
`no-brain` leaves out the `mxcli brain` section. `off` makes `context-pack.sh` exit 3 and the
dispatcher falls back to the reading list in `iterative-build-loop.md`, so a CLI change that
breaks `DESCRIBE` or `brain brief` is switched off with one line in `PROJECT.md`.

**Older briefs.** A module brief with no `### Build steps` table, written before packs existed,
also exits 3 and falls back to the reading list ([#202](https://github.com/MendixMau/mxcli-project-toolkit/pull/202)). A project mid-build keeps going after a pull
without retrofitting its briefs.

## 4. Everything else

### Reports and visibility

- **One progress report replaces `build-plan.html`.** `architecture/progress-report.html` is a
  single self-contained page. It keeps what the old page showed (phases, built and proven) and
  adds stages P to 6 with links to their artifacts, a progress bar and a stage nav
  ([#434](https://github.com/MendixMau/mxcli-project-toolkit/pull/434)).
  - Session logs are optional. Without one, time and token data are marked unavailable. With a
    Claude Code session log it adds time per stage, sub-agent use, context size and an estimated
    token and cost figure.
  - A session cache makes a refresh take about a second.
  - Autoreload keeps your scroll position, and only runs while a build is active.
  - Tips sit in a side column, grouped by theme and collapsed by default, with calm severity.
  - An old `build-plan.html` is still accepted and never deleted.
- **`build-plan.json` stays current.** `build-plan-status.sh --refresh` updates an existing
  `build-plan.json`, so a day of building no longer reads as 0 built
  ([#437](https://github.com/MendixMau/mxcli-project-toolkit/pull/437)).
- **A bug log you can file safely.** `docs/bugs.jsonl` per project and `bin/file-bugs.sh`, which
  redacts every title and body, searches for duplicates, and posts only after you confirm each
  bug at a terminal ([#433](https://github.com/MendixMau/mxcli-project-toolkit/pull/433)).
- **Change requests stay visible.** A change request updates the module brief and shows as
  "waiting" at session start and module close until it is built
  ([#430](https://github.com/MendixMau/mxcli-project-toolkit/pull/430)).

### Process map and BRD report

- **Process map.** One swimlane map per business process, each step on its wireframe once
  screens exist, every open question and `ASSUMED` decision pinned to the step it is about. It is
  drawn twice: a draft at Stage 2 close (shown at CAC-3) and the full map at Stage 3. In the
  field run that prompted it, the reviewer could not tell where sixty questions fit; the map
  placed 102 items with 0 unplaced ([#429](https://github.com/MendixMau/mxcli-project-toolkit/pull/429)).
- **BRD report with the map on top.** The Stage 2 report opens with the process map and lists
  requirements and open questions under it, each tied to its step. A click on a step filters the
  list, and what no step covers stays under "whole app". `open-questions.html` is retired, and
  the Stage 3 prototype and the map link to each other
  ([#438](https://github.com/MendixMau/mxcli-project-toolkit/pull/438)).
- **Follow-ups.** Migrating an old anchors file no longer trusts a regex: it checks what changed,
  says what it did, accepts a string `targets`, and lists unfilled entries instead of dropping
  them ([#453](https://github.com/MendixMau/mxcli-project-toolkit/pull/453)).

### Skills learned

- **`rest-between-mendix-apps`**: for two or more Mendix apps that read each other over REST. A
  contract to write down before the first script, 17 publisher and consumer rules, and a
  six-rung cross-app test ladder
  ([#273](https://github.com/MendixMau/mxcli-project-toolkit/pull/273)).
- **`demo-recording-polish`**: 60 fps capture, a drawn cursor with a click ripple, eased scroll,
  and a zoom rendered after the take, so re-framing re-renders the same take
  ([#404](https://github.com/MendixMau/mxcli-project-toolkit/pull/404)).
- **Workflow notes**: a Jump has one fixed target, so one failure handler for several steps is a
  child workflow; three probed build errors; workflow seed reset
  ([#415](https://github.com/MendixMau/mxcli-project-toolkit/pull/415)).
- **Skill trims.** Five skill findings (detection gaps, date tokens, Atlas selectors, grants for
  the default home page, CSS traps) landed as compact rows paid for by trimming provenance
  prose, so the always-loaded total went from 75,225 to 75,204 words
  ([#422](https://github.com/MendixMau/mxcli-project-toolkit/pull/422)).
- **`load-test`**: load test a page without correlating Mendix's client protocol by hand.
  Playwright records the real `/xas/` calls, a probe maps each opaque `runtimeOperation` to its
  microflow through Jaeger, and the chosen call is replayed with the session's own cookie and
  CSRF token. It lists ten field traps and a four-line report that says what the run does not
  prove. No instrument ships yet, only the skill
  ([#431](https://github.com/MendixMau/mxcli-project-toolkit/pull/431)).
- **`unit-test`**: how to write and run a microflow unit test whose assertion is live: what is
  worth a test and what is not, equality-only `@expect`, a positive control that must fail, and a
  four-line report. Whether and when unit tests run stays with the project's test strategy
  ([#432](https://github.com/MendixMau/mxcli-project-toolkit/pull/432)).
- **`learned-multilingual-app`**: a second language is four decisions the translations never see: source
  language, enabled languages, the user's starting language, and a switch a normal role can use.
  A field run wrote 418 strings per language correctly and the language picker still failed with
  every check green. The skill gives the recipe and the traps
  ([#449](https://github.com/MendixMau/mxcli-project-toolkit/pull/449), from #387 by CarlesZ).
- **Five legacy-widget field notes** from an existing-app rebuild went to the inbox for triage
  (first proposed as [#309](https://github.com/MendixMau/mxcli-project-toolkit/pull/309), landed
  as [#450](https://github.com/MendixMau/mxcli-project-toolkit/pull/450), thanks to AlvinnYeo).
- **Decompose and rehost.** Three on-demand skills for working from an existing Mendix app:
  `decompose-app` (split a monolith into several apps, choosing the cut on business fit and
  coupling), `rehost-app` (regenerate a whole `.mpr` into a fresh app with `pipelines/mendix-mpr/`
  and read the fidelity ledger) and `mendix-service-seam` (OData and REST patterns between two
  Mendix apps). `bin/cut-score.sh` scores a proposed split and prints a clean, costly or blocked
  verdict per partition, and `bin/cut-ledger.sh` writes one row per crossing edge and exits 1
  while any edge has no resolution
  ([#341](https://github.com/MendixMau/mxcli-project-toolkit/pull/341), [#342](https://github.com/MendixMau/mxcli-project-toolkit/pull/342), [#345](https://github.com/MendixMau/mxcli-project-toolkit/pull/345), [#346](https://github.com/MendixMau/mxcli-project-toolkit/pull/346)).
- **`mxpatch` and the hash check.** `project-bin/mxpatch.py` is a shared patch core that finds a
  unit or element, changes a value and writes the unit and its `.mpr` ContentsHash in one step.
  `exec.sh --patch` now runs `mxcli fix hashes` before and after the script, so the two shipped
  workflow patchers no longer leave a stale hash
  ([#374](https://github.com/MendixMau/mxcli-project-toolkit/pull/374), from jopterhorst).

### Fixes

- **A crashed mxbuild rolls the write back.** When a baseline was measured and mxbuild then
  exits non-zero without an error list, `exec.sh` restores the snapshot and logs one row, instead
  of keeping a model nothing can load
  ([#424](https://github.com/MendixMau/mxcli-project-toolkit/pull/424)).
- **Sync keeps your `.claude/settings.json` rules.** A re-wire runs `mxcli init`, which
  overwrites that file. `wire-agents.sh` now merges: your entries win and keep their order, and
  entries only the new file has are appended
  ([#421](https://github.com/MendixMau/mxcli-project-toolkit/pull/421)).
- **The macOS sync fix.** The exec-approval rewrite failed on stock macOS awk while sync printed
  "Rewrote" on every run. It now works there and prints a `WARN:` when a rewrite fails
  ([#427](https://github.com/MendixMau/mxcli-project-toolkit/pull/427)).
- **The right JDK for your Mendix version.** `find_java` asks for JDK 25 on Mendix 11.14 and
  newer, JDK 21 otherwise, and a warning names a missing JDK
  ([#410](https://github.com/MendixMau/mxcli-project-toolkit/pull/410)). It adds about 45 ms
  per exec when `JAVA_HOME` is unset.
- **The look-ledger hook comes back.** A project whose `.claude/settings.json` lost the
  look-ledger hook (so the ledger read 0 of 31 pages seen with 22 screenshots on disk) gets it
  restored by sync, and `doctor.sh` warns. Opt out with `.mxtk/no-hook-repair`
  ([#414](https://github.com/MendixMau/mxcli-project-toolkit/pull/414)).
- **A staged-secrets check.** `check-staged-secrets.sh` compares your project's real secret
  values against staged blobs and prints the file and key name, never the value. On a synthetic
  6,000-file repo, 230 staged files take 1.0 seconds and a whole-tree scan 2.6
  ([#411](https://github.com/MendixMau/mxcli-project-toolkit/pull/411)).
- **`exec.sh` locks per project**, offers `--commit-first`, ends every applied script with a
  restart verdict, and `bin/app-restart.sh` restarts only this project's own `run --local`
  ([#304](https://github.com/MendixMau/mxcli-project-toolkit/pull/304),
  [#324](https://github.com/MendixMau/mxcli-project-toolkit/pull/324),
  [#322](https://github.com/MendixMau/mxcli-project-toolkit/pull/322)). In a 20-task field run,
  57 of 148 `exec.sh` runs had applied nothing, and a different project's write had blocked
  another. A fixture runs 10 rounds of 12 contenders and asserts at most one lock holder.
- **Merges no longer need `--no-verify`.** The doc numbering check examines only files a merge
  itself changes
  ([#418](https://github.com/MendixMau/mxcli-project-toolkit/pull/418)).

#### Quality gates

- **Every merge is reviewed by someone who did not write it** (MERGE, MERGE-AFTER-FIX or HOLD,
  on value, regression risk after sync, correctness and context cost). Nine PRs had merged on
  2026-10-13 without one ([#316](https://github.com/MendixMau/mxcli-project-toolkit/pull/316)).
  Several fixes in this release came out of those reviews. Every PR now also states its cost in a
  five-row Impact block ([`docs/RELEASE-PROCESS.md`](../RELEASE-PROCESS.md) §4a).
- **A missing navigation item fails the journey.** `navTo` throws
  `navigation item "<title>" not found` instead of clicking nothing, so a control that must fail
  can no longer pass. Replayed on a five-app project, none of the 26 real journeys turned red and
  the 4 deliberately broken controls now fail
  ([#412](https://github.com/MendixMau/mxcli-project-toolkit/pull/412)).
- **Lint you can trust and tune.** UX001/002 and Batches 1 to 4, including SEC014 (an external
  role that can write status, audit or ownership members). When `mxcli init` reverts toolkit
  rules to stock, the lint gate stops as BLIND instead of blaming the next script
  ([#238](https://github.com/MendixMau/mxcli-project-toolkit/pull/238),
  [#305](https://github.com/MendixMau/mxcli-project-toolkit/pull/305),
  [#308](https://github.com/MendixMau/mxcli-project-toolkit/pull/308),
  [#312](https://github.com/MendixMau/mxcli-project-toolkit/pull/312)).
- **End-to-end proof that fails for the right reason.** The journey runner preflights the suite
  and journeys can declare `requires`, `leaves` and `consumes`. OQL rows are read by SELECT alias,
  an app that dies mid-suite reads APP-DOWN rather than FAIL
  ([#302](https://github.com/MendixMau/mxcli-project-toolkit/pull/302),
  [#310](https://github.com/MendixMau/mxcli-project-toolkit/pull/310),
  [#319](https://github.com/MendixMau/mxcli-project-toolkit/pull/319)).
- **Themed palettes compare correctly.** `check-design-reaches-app.sh` compares a design system
  whose palette lives in scoped blocks such as `:root.theme-light` block for block, and no longer
  warns "0 of N tokens carry the design's value" on a correct port
  ([#423](https://github.com/MendixMau/mxcli-project-toolkit/pull/423)).
- **Stage 3 designs how users reach each page.** `design/interaction-model.md` comes before the
  first wireframe: a home per role, an inbox per user task, and per page how it is reached and
  what it receives ([#317](https://github.com/MendixMau/mxcli-project-toolkit/pull/317)).
- **Changing an existing app** reports the delivery round from a `## Rounds` table, logs
  mid-build feedback as a change-log row before any edit, and owes a final whole-app LOOK at
  Stage 6 ([#326](https://github.com/MendixMau/mxcli-project-toolkit/pull/326),
  [#306](https://github.com/MendixMau/mxcli-project-toolkit/pull/306),
  [#303](https://github.com/MendixMau/mxcli-project-toolkit/pull/303)).

### Known gaps

- **Field runs still owed.** Fixtures pass, but no real-project run is cited yet for the
  property-set check, the page-fidelity rescoring, per-BRD conformance ledgers, the incremental
  app map, and the test strategy end to end (the A/B that compares a scripted change on a lab
  copy against master).
- **A defect a module-close full run used to catch may now surface only at the full run** before
  deploy. That is the trade the test strategy makes.
- **[#291](https://github.com/MendixMau/mxcli-project-toolkit/issues/291) parts 2 and 3** (gate
  facts for the interaction model, and the model-side check) are not built.
- **`affected-tests.sh` in a multi-app folder** over-reaches because module names can repeat
  across apps.
- On Windows and Linux without Studio Pro, `exec.sh` skips its mxbuild gate unless mxbuild is
  found; run `bin/doctor.sh --install <project>` or set `MXBUILD_PATH`.

## 5. How to update

Pin the toolkit clone to the tag `v1.0`, then sync each project:

```bash
git -C ~/Mendix/mxcli-project-toolkit fetch --tags
git -C ~/Mendix/mxcli-project-toolkit checkout v1.0
~/Mendix/mxcli-project-toolkit/bin/sync-project.sh <project-root> --repair-intake
```

The checkout is detached on purpose: a pinned clone stays on the tag. The session-start ritual
runs `git pull --ff-only`, which fails off a branch and warns that the clone is not on `master`;
that warning is expected. To unpin:
`git -C ~/Mendix/mxcli-project-toolkit checkout master && git -C ~/Mendix/mxcli-project-toolkit pull`.
Skills update with the checkout. Sync refreshes what was copied into the project and prints the
`Toolkit release:` you are on. `--repair-intake` is needed where the project predates the new intake questions: it appends the
questions older projects lack, numbered after the highest one present (Q13, unit tests default,
in a fresh project). An appended question must be answered, because an unanswered one fails the
Stage P gate. The README's plain update is `git pull` followed by
`bin/sync-project.sh <project-root>`; the pinned form above is the one for stability
([`docs/RELEASE-PROCESS.md`](../RELEASE-PROCESS.md) §8).

**After updating:**

- Answer SEC014's question (which roles are external), then re-baseline lint once, as the sync
  NOTE says.
- On mxcli v0.26 or later, sync runs a read-only property-set check. If it reports a repair is
  needed, run `bin/doctor.sh --fix-property-sets <project>`
  ([#314](https://github.com/MendixMau/mxcli-project-toolkit/pull/314)).
- Projects with per-BRD coverage ledgers: run conformance once; old rows are re-keyed
  ([#307](https://github.com/MendixMau/mxcli-project-toolkit/pull/307)).
- `oqlScalar` now returns the first SELECT alias. A journey that relied on `navTo` silently
  clicking a missing item now fails at the nav step.
- If you installed the interview-gate hook earlier, re-run `bin/install-claude-hooks.sh --full`. The
  old copy in `~/.claude/hooks` calls `bin/questions-report.sh`, which is removed, so it would write
  no report.
- Sync adds `/.claude/progress-report-sessions.txt` to `.gitignore`; commit that line. An old
  `build-plan.html` and `docs/open-questions.html` are left in place and can be deleted.
- `PROJECT.md` `## Test strategy` is not written by sync. A project with no such section uses
  the printed defaults and says so.

**If you cannot update today**, paste this into your session:

> Do not run mxcli test, unit tests or the full journey suite after individual fixes. After each
> fix, run only the affected tests (./bin/affected-tests.sh <script>). Run the full suite once when the build is complete,
> and again before each deploy.
