  • Unknown — cannot be assessed yet; needs a spike.

Recommended Scope Subset

Step 4 of source-triage.md. A slice is an ordering, not an exclusion. The whole source is always in scope; this section decides sequencing, not what gets dropped. Do not force POC framing onto a project committed to a full migration — the decision (which capabilities go first) is the same either way.

Two things this recommendation must NOT rest on alone: extraction cleanliness (the easiest capability to automate is not automatically the right one to migrate first — ask the user about business priority), and "everything is Ready, so do it all at once" (a large first slice needs the same dependency and priority reasoning as a small one).

Format: capability -> verdict -> recommended for this slice (yes/no/deferred) -> why.

Whole documented scope is in (per intake Q4), ordered as one slice covering everything except pilotage/tug scheduling (explicitly out of scope, ch04). Ordering below is what CAC-1 (scope brainstorm) confirmed and what Stage 4's build plan sequences:

  • Vessel & agent registry -> N/A (text-native) -> yes, first -> every other capability references Vessel/ShippingAgent; no dependencies of its own.
  • Berth & terminal master data -> N/A -> yes, first -> same reasoning; BookingRequest and Tariff both depend on Berth/Terminal.
  • Booking request lifecycle -> N/A -> yes, second -> the core transaction; depends only on the two master-data capabilities above.
  • Officer review & approval -> N/A -> yes, third -> depends on BookingRequest existing.
  • Tariffs & invoicing -> N/A -> yes, third (parallel with review) -> depends on Terminal + BookingRequest, not on the review outcome itself (fee calc is independent of approval).
  • Inspections & departure clearance -> N/A -> yes, fourth -> depends on BookingRequest being Approved (dangerous-goods gate) and interacts with Tariff (surcharge relief).
  • Notifications -> N/A -> yes, cross-cutting, built alongside booking lifecycle -> low effort, high visibility to agents from day one.
  • Audit & compliance -> N/A -> yes, cross-cutting, built alongside each entity -> the audit row must exist before any status-changing microflow does, not bolted on after.
  • Security & access -> N/A -> yes, first (with master data) -> per security-is-not-a-later-script.md, entity + grants land together, so role scoping has to be in place before any entity that needs it is built.
  • Reporting -> N/A -> yes, last -> read-only over data the other capabilities produce; no value until they exist.
  • AIS integration -> N/A -> deferred -> integrations dimension rated named not specified (no protocol/auth/failure-mode in the source); recommend building a stub first and wiring the real feed once a contract exists (see Open questions / Stage 3 fit-gap).
