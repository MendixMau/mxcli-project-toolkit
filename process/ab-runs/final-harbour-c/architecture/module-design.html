Module Design Rationale

Per modularize-domain.md. Five modules, decided on their own merits (never 1:1 from the source's chapter structure) against the Step 2 boundary criteria. Unattended run (final-harbour-c) — this document is the sign-off surface; the four Step 1 questions below still need a returning human's confirmation (recorded ASSUMED in PROJECT.md until then).

HB_MasterData Common

Mission: Reference data — vessels, shipping agents, terminals, berths.

Business process / journeys
Agent registration & onboarding (ch11); berth/terminal upkeep by Harbour Master (ch12).
Users / roles
Read by all four roles; write restricted to Berth Officer (activate agent) and Harbour Master (reactivate, berth/terminal maintenance).
Closely-tied data
Vessel, ShippingAgent, Terminal, Berth — Berth_Terminal and Vessel_ShippingAgent associations both intra-module.
Dependencies
Imports nothing (bottom of the graph). Every feature module imports it.
Criterion earned
Bounded context (reference/master data is its own thing) + reuse (every other module reads it).
Rejected alternative
Folding Vessel/ShippingAgent into HB_Booking — rejected because Vessel and ShippingAgent are referenced by three modules (Booking, Finance via Invoice, Inspection indirectly), not one; keeping them Common avoids three copies of the same lookup data.

HB_Booking Domain + Logic

Mission: The booking request lifecycle — creation, submission, officer review, approval/rejection/override, cancellation, AIS arrival flag.

Business process / journeys
J-01 (Draft → Review → Approve/Override), most of J-02.
Users / roles
Shipping Agent (create/edit/cancel own), Berth Officer (queue, review, decide), Harbour Master (override).
Closely-tied data
BookingRequest, ApprovalDecision — always used together (every ApprovalDecision belongs to exactly one BookingRequest, and a booking cannot be understood without its decisions).
Dependencies
Imports HB_MasterData (Vessel/ShippingAgent/Berth), HB_Reporting (audit log). Exposed to HB_Finance and HB_Inspection via cross-module associations they own.
Criterion earned
Bounded context (the core transactional capability) + independent lifecycle (this is the module most likely to change release-to-release).
Rejected alternative
Splitting Review into its own module (HB_Review) — this was the first draft. Rejected: BookingRequest and ApprovalDecision are the textbook "always used together" over-split signal from modularize-domain.md's own cautionary example (PROJECT-H) — splitting them forces a cross-module association for data that is 1:1 coupled, plus a bespoke cascade concern on delete. Merged back into one module.

HB_Finance Domain + Logic

Mission: Tariffs, fee calculation, invoicing.

Business process / journeys
Tail of J-01 (invoice generated on Completed, Paid/Void).
Users / roles
Harbour Master (tariff maintenance, mark Paid/Void, waive surcharges), Berth Officer (waive late-arrival only), Shipping Agent (view own invoices).
Closely-tied data
Tariff, Invoice — Invoice_Tariff intra-module.
Dependencies
Imports HB_MasterData (Terminal, ShippingAgent), HB_Booking (reads BookingRequest for fee inputs; owns Invoice_BookingRequest), HB_Reporting.
Criterion earned
Bounded context (billing is a distinct business capability from booking operations) + security segregation (Harbour-Master-only actions concentrate here).
Rejected alternative
Merging into HB_Booking — rejected: billing rules (VAT, surcharges, invoice due-dates) change on a finance-team cadence independent of the booking workflow, and mixing them would make one module owned by two different concerns.

HB_Inspection Domain + Logic

Mission: Scheduling and recording inspections; gating dangerous-goods approval and departure clearance.

Business process / journeys
Middle of J-01 (Inspect → Clear).
Users / roles
Inspector (schedule, record, complete); Berth Officer (grant clearance, reads Outcome).
Closely-tied data
Inspection, InspectionItem — intra-module (InspectionItem_Inspection).
Dependencies
Imports HB_Booking (reads CargoClass/Status; owns Inspection_BookingRequest), HB_Reporting.
Criterion earned
Bounded context (a distinct compliance/safety domain, its own actor — Inspector — touches nothing else) + security segregation.
Rejected alternative
Folding into HB_Booking — rejected: Inspector is a role that touches no other booking data directly, and inspections have their own scheduling/calendar UI unrelated to the booking form.

HB_Reporting Common

Mission: The shared audit-log service every other module calls, plus the monthly CSV report.

Business process / journeys
Cross-cutting — not a journey of its own, called from every status-changing microflow in the other three feature modules.
Users / roles
Harbour Master + Berth Officer view reports; AuditEntry has no dedicated end-user screen.
Closely-tied data
AuditEntry only — deliberately generic (EntityName + RelatedReference, not a hard association — see architecture decision F007-Q1).
Dependencies
Imports nothing. Called by HB_Booking, HB_Finance, HB_Inspection.
Criterion earned
Reuse — an audit-logging module is exactly the kind of thing that gets lifted into another app as-is, even though it "owns" only one entity (the over-split signal "~1 entity and nothing reusable" does not apply here — this one entity IS the reusable thing).
Rejected alternative
No shared audit module at all, each feature module keeping its own log — rejected: the source (ch26) explicitly describes ONE audit trail across booking/decision/invoice/inspection events, not four separate logs.

Does this match how your teams and processes are actually organized?

Four questions this document cannot answer from the source alone (modularize-domain.md Step 1) — answered here provisionally (unattended run) and recorded ASSUMED in PROJECT.md, pending a returning human:

  1. Team ownership — no team structure is named anywhere in the corpus; assumed one team builds/owns the whole app (small app, no signal otherwise).
  2. Reuse intent — HB_Reporting's audit-log pattern is the only module built with an eye to reuse in another app; nothing else is flagged for lift-out.
  3. Release cadence — no independent-release signal in the source; assumed one release train for all five modules at this stage.
  4. Security/regulatory segregation — the only segregation signal is company-row-security (F001, ch35) and role-gated actions (Harbour Master overrides/waivers) — both already reflected in the module boundaries above, no additional PII/regulatory split needed.
