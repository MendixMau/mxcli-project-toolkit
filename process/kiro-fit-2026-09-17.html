Kiro and the Toolkit

Does AWS's spec-driven IDE earn a place beside the runbook, the gates and ./mxcli — or does it fight them?

17 Sep 2026 Evidence: secondary sources only Prior art: PR #75 (draft)
Verdict

Support it as a consumer. Don't adopt it as the process.

Kiro reads a repo's instructions well enough that the toolkit's existing pointer — the steering file already written in PR #75 — is the whole integration. That's cheap and worth finishing. What it cannot be is the pipeline: Kiro's spec mode wants to own requirements → design → tasks, which is precisely the ground the runbook's nine stages, BRDs and gate-check.sh already hold, and its permission model puts the exec-approval work outside the repository's reach.

Confidence is moderate, not high. Nothing below has been run in Kiro. kiro.dev is egress-blocked from this container — the same wall PR #75 hit in August — so every claim here comes from search summaries and third-party write-ups, not first-party docs. Two of them contradict what PR #75 currently says.

The stack

How the pieces fit

Nothing about the toolkit is tied to one IDE. Every agent reads a committed pointer file, every pointer defers to CLAUDE.md, and from there the process layer decides what gets built and what may run. Kiro slots into the top band like the other five — and then forks.

New finding

Kiro's permissions live outside the repository

This changes two things already written

Kiro 1.0's capability permissions resolve from ~/.kiro/settings/permissions.yaml for user rules and ~/.kiro/workspace-roots/<hash>/permissions.yaml for workspace rules — the workspace file is keyed by a hash of the path and stored in the home directory, not in the checkout. Effects are allow / ask / deny with deny-overrides; the shipped default allows fs_read on ./** plus read-only git and system commands, which does not cover ./mxcli exec or bin/*.sh.

Consequence 1 — a cloned project cannot ship a Kiro allowlist. That puts Kiro with Cursor and Windsurf in install-harness-permissions.sh's table (no write, document it), not with Claude, Copilot and Aider (write a committed file). Worth folding in while PR #85 is still open.

Consequence 2 — PR #75's steering preamble points the human at .kiro/settings/ for the allowlist. As far as the sources go, that path is wrong. Fix the line before the PR flips to ready, or it ships a wrong instruction to every wired project.

The real hazard

Two pipelines, one project

Everything else is wiring. This one is structural. Kiro's headline feature is spec-driven development: it turns a prompt into a requirements document, then a design, then a task list, and works the tasks. That is a good idea and it is the same idea the runbook already implements — with stage gates, a decision register in PROJECT.md, obligation checks that refuse to go green by absence, and a source ledger that blocks Stages 1–2 until every source file names the artifact that consumed it.

Let both run and a project has two sets of requirements that drift apart, which is the exact failure the drift-sync rule exists to catch — except this drift would be between the toolkit's BRDs and a directory the toolkit never reads. The steering file already forbids it in one sentence. Whether one sentence holds against a mode the IDE actively promotes is the single question a field run would answer, and it's worth more than the rest of the test put together.

  • Watch for unrequested .kiro/specs/ directories appearing during a normal build session.
  • If they appear anyway, the fix is a .gitignore line plus a louder steering sentence — not abandoning the integration.
  • Kiro's hooks (agentSpawn, userPromptSubmit, preToolUse, postToolUse, stop) could enforce it mechanically, but that's a second integration and shouldn't gate the first.

Recommendation

What I'd actually do

  1. Fix the allowlist path in PR #75 before anything else

    One line in the steering preamble. It currently points at .kiro/settings/; the workspace permission file appears to live under ~/.kiro/workspace-roots/<hash>/. Shipping a wrong path is worse than shipping no path.

  2. Add the Kiro row to install-harness-permissions.sh in PR #85

    Same treatment as Cursor and Windsurf: no file written, a documented note saying where the human puts the rule. #85 is open and the table is right there.

  3. Do the 30-minute field run, once

    Open a wired project in Kiro on the free tier. Confirm the steering file loads into the conversation, that a gate question renders and actually stops, that ./mxcli -c "SHOW MODULES" can be allowed without per-call prompting, and — the important one — that it does not spawn .kiro/specs/ unasked.

  4. Then flip #75 to ready and merge it

    It's opt-in behind --with-kiro, writes nothing unless asked, and its fixture is green. Post-field-run it costs the toolkit nothing to carry.

  5. Leave custom agents and headless alone for now

    Porting six agent stubs into .kiro/agents/ and wiring kiro-cli into CI are each real projects. Neither pays off until someone is genuinely working in Kiro daily. Revisit if that happens.

Caveat

What this page is not

Held to the toolkit's own bar, this is a claim, not a check

The repo's rule for shipping an instrument is that it runs against real input once and the commit names where. Nothing here has run against Kiro. kiro.dev is unreachable from this environment, so the permission paths, the hook names, the credit costs and the CLI flags all come from secondary sources and could be stale — Kiro moved from Amazon Q Developer, went international in May 2026, and hit 1.0 with a permission model that didn't exist in earlier builds.

Treat the verdict as a direction — support, don't adopt — and treat every specific path in it as something the field run has to confirm.
