Kiro in the Loop

Kiro is an IDE. The runbook is a process. mxcli is the only thing that writes to the .mpr. They occupy three different layers, so they can stack — but Kiro's spec mode wants to own three stages the runbook already owns, and that is where the value and the trouble both sit.

The parties

Three parties, three jobs

Kiro The seat

An agentic IDE. Reads .kiro/steering/*.md at every turn, can fire hooks around tool calls, and drafts. It is a place an agent sits — interchangeable with any other seat, in principle.

The pipeline The authority

Nine stages, four ✋ gates, one decision register in PROJECT.md, and the drift-sync rule. Lives in markdown and shell, so it is seat-agnostic by construction — that is the whole point of it.

mxcli The hand

The only writer. check validates a script, bin/exec.sh snapshots then executes then runs mxbuild and restores on failure. Nothing else may touch the model.

Upside

What Kiro could actually buy us

Now

A second seat, for free

The steering file already merged in the open PR points Kiro at the runbook the same way AGENTS.md and .cursorrules do — a pointer, never a copy. That makes Kiro a fifth supported seat at the cost of one generated file, and costs nothing if nobody uses it.

Watch

Hooks could make the discipline mechanical

Every rule in the toolkit that currently depends on an agent choosing to obey — snapshot before exec, never git add -A, ask the gate question and stop — is a rule a preToolUse or stop hook could enforce instead of request. That is the one capability no other seat we support has. See Figure B, and read the caveat under it.

Later

The six agent roles have a native home

Kiro's custom agents take the same shape as the roles we already scaffold — ba, architect, mdl, gate, test, review. A generator could emit them from the same source the existing stubs come from.

Now

Standard MCP, so mxcli's server just works

Kiro speaks ordinary MCP with per-agent tool scoping, so the MCP write modes the preflight table calls for need no new plumbing — only a config file.

Downside

Where it bites

Conflict

Spec mode competes for Stages 2–4

Kiro's requirements → design → tasks flow lands in .kiro/specs/<feature>/ and covers Requirements, Architecture & Design and Build Plan — two of the four ✋ hard gates. Run both and there are two requirement sets, two designs, two plans, and no answer to which one a gate reads. The runbook's "one decision register" rule is not a preference; it is the thing that keeps a build from regressing itself.

Blocked

The permission allowlist cannot ship in the repo

Workspace capability rules live under a hashed path in the user's home directory, outside the checkout. So a clone can carry steering files and agent definitions but not its own allowlist — every user re-grants by hand. Any pitch resting on "the repo configures Kiro safely" fails here. (The steering preamble in the open PR still names the wrong directory for this.)

Cost

Metered, and our stages are not small

Credits per spec run, not per seat. A complex spec run is a double-digit credit charge, and the pipeline's stages are larger than the runs that number was quoted for. The per-build cost is a number nobody here has measured.

Drift

Two copies of six agent roles is a copy, not a pointer

The toolkit's own authoring rule is pointers, never copies — the per-tool instruction files are pointers precisely because copies drift. Native Kiro agents would be a second set of role definitions to keep in step, which is how the three-copy enrichment-report defect happened.

Gating

Nothing here has been field-run

Every fact on this page is secondary-source; the vendor's own docs are unreachable from this environment. The toolkit's ship bar requires one real run, cited, against real input. Until someone drives one module end to end in Kiro against a real model, everything above is a claim.

Three postures

Adopt

A · Kiro as a second seat

Generate the steering pointer, fix the allowlist path it names, drive one real module through it, cite that run. Reversible, cheap, and the work is mostly done.

Park until proven

B · Hooks as an enforcement layer

The genuinely interesting idea — mechanical discipline instead of requested discipline. But it is a blocking instrument, so it has to accept evidence it did not create and must never block its own remedy. Build it after A has run, not instead.

Refuse

C · Spec mode instead of Stages 2–4

Trades four ✋ gates, one decision register and the drift-sync rule for a vendor's spec folder. There is no version of this that does not end in two sources of truth.
