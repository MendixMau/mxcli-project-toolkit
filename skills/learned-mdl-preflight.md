# MDL Pre-flight Checklist — STOP conditions before writing any script
**Applies to:** any mxcli project.
**Purpose:** Before drafting any MDL script, check every planned operation against this table. Each STOP row was born from a real MPR corruption or silent runtime failure — not theoretical concerns. Skipping this check has caused project-unloadable corruption every time.

**Source:** Generalized from a live Mendix 11.12.0 Beta project, 2026-07-06/07. Incident detail stays in that project's own `bug-logs/` — only the generalizable rule is here.

**Version context:** Rules marked "STOP" were confirmed on specific mxcli/Mendix versions noted per entry. Rules 1b and 10 were retested 2026-07-09 on mxcli v0.13.0 / Mendix 11.12.0 and confirmed resolved. Rule 9 was retested 2026-07-09 via `mxcli --mcp` on v0.13.0 and confirmed resolved (BSON serialization bug only affects the disk write path; `--mcp` bypasses it entirely). If in doubt, retest on your version and stamp the result in `bug-logs/mxcli-bugs.md`.

**v0.20.0 deltas (retested 2026-08-31, [bug-logs/mxlabs-v0.20.0-retest-2026-08-31.md](../bug-logs/mxlabs-v0.20.0-retest-2026-08-31.md)) — on a project whose mxcli is ≥ v0.20.0:**
- **Rule 17 (uppercase `AND`/`OR` + `!=`) is resolved** — builds at 0 errors; keep the lowercase habit only for projects pinned to older binaries.
- **Rule 1c's class (ALTER PAGE `SET Editable`/conditional settings) is resolved** — `SET Editable = [expr] ON widget` stores correctly and the project loads.
- **ALTER PAGE now requires the braced block form** `ALTER PAGE Mod.Page { SET … ON w; };` — the old flat `alter page X set … on w;` is a parse error. DataGrid2 columns are addressed by **derived** name (bound attribute, else caption — MDL-WIDGET16), and a bare column name in REPLACE is refused in favour of `grid.column`.
- **Still corrupting, STOP stays:** workflow `DECISION` activities (BUG-76 — project unloadable, `EnumerationValueIdentifier`), and `marketplace install` on a split-model project (#879, unfixed in v0.19/v0.20).
- The 10–12-writes-per-session cap from BUG-97 is downgraded to snapshot-plus-read-back: 16 sequential writes were clean on v0.20.0.
- **Rule 2 (settings/security-level writes) is resolved** — probe-verified 2026-08-31: `alter project security level production`, `alter project security demo users on`, `alter project security guest access off` (guest access is new v0.19 surface — anonymous access was previously read-only), `alter settings model FirstDayOfWeek = Monday` and `alter settings configuration … HttpPortNumber` all land, read back, and cold-load at 0 errors. **Project security setup is now a scriptable project-start step, not an end-of-build Studio Pro chore** — see `brd-to-build-plan.md` Step 5's scaffold row.

## Step 0 — choose the write mode (do this first, before the STOP table)

There are three write modes, and they are **co-equal tools chosen by the shape of the work** — not one default plus two fallbacks. Pick the mode from the task first; *then* use the STOP table below only as the safety overlay that overrides your pick for the handful of operations mxcli corrupts. "CLI unless forced to MCP" is the wrong mental model — it is why projects drift to CLI-only and never touch the live-editing loop.

| Mode | Command | Reach for it when | SP |
|---|---|---|---|
| **CLI** (disk write) | `./mxcli exec script.mdl` | Bulk, structural, done-once: a whole domain model, a module's microflows, access rules, navigation, demo users. One script scaffolds a lot. | Closed |
| **MCP + MDL** | `./mxcli --mcp http://localhost/mcp --mcp-dial localhost:7782 exec script.mdl` | Iterative refinement and UI tuning where restarting SP per change would kill flow — page layout, widget wiring, visibility expressions. Live edit, no recompile wait. Also the required path for rule 9 (inline assoc-sets). | Open |
| **Hand-rolled MCP** | `pg_patch_page`, `ped_create_document`, `ped_update_document` | Widget JSON shapes MDL has no syntax for — rules 1, 6, 6b, 7 and datagrid customContent conditionals. Confirmed payloads in `learned-mcp-patterns.md`. | Open |

**Typical module rhythm:** one CLI exec to scaffold domain + microflows → MCP+MDL for page iteration and UI tweaks → hand-rolled MCP only for the specific widget shapes MDL can't reach. A project that only ever runs CLI is usually leaving the fast UI-iteration loop on the table, not being more disciplined.

**When more than one mode genuinely works** — most page changes and most single/small microflow builds fall in this zone — don't silently pick one. Name the viable modes (CLI / MCP+MDL / hand-rolled MCP — remember MCP splits into these two: MDL run through the MCP connection, or direct `pg_patch_page`/`ped_*` calls with no MDL at all), give a one-line recommendation with reason (e.g. "MCP+MDL, since SP is already open and this is a small widget tweak" / "CLI, this is a whole-module scaffold"), and let the user pick before executing. Only skip asking when the STOP table forces a mode, or the user has already stated a standing preference for that exact operation type in this session/project. Default lean, absent other signal: MCP for page edits and small microflow builds, CLI for bulk/structural work (domain models, access rules, navigation, demo data).

Once you've picked a mode per operation, run the STOP table below against every one of them — it overrides your pick whenever an operation falls in the corrupting set.

**Also decide, per document, where it lands.** Any operation that *creates* a document — page, snippet, microflow, nanoflow — needs its folder chosen now and written into the `folder` property of the same statement, not fixed afterwards. Read the path off the brief's `### Document folder plan`; when there is no row for it, derive it per `module-folder-convention.md` ("Deciding the path"), and escalate rather than guess when the feature group is unclear. Omitting `folder` is legal MDL that silently drops the document at module root — no error, no gate, and a cleanup job later that nobody schedules.

**Companion skills:** `learned-mcp-patterns.md` (MCP alternatives), `bug-logs/mxcli-bugs.md` (bug detail), `iterative-build-loop.md` (exec discipline), `learned-microflow-patterns.md` (annotation + inline assoc rules)

A `log info` activity using `toString(count($ActiveRoutes))` passed `mxcli check` but failed `mx check`/SP with CE0117. It is unclear whether the 2026-07-09 retest actually exercised a real `count()` call or a different construct; treat `count()` as unverified and prefer `length($list)` until re-confirmed. |
| 11 | Filter an XPath with an association-traversal as the comparand: `[Assoc_X = $Ctx/Other.Assoc]` | **STOP → retrieve target first, then filter** | XPath constraint right-hand side must be a directly-bound variable, not an association path. | 12 | Write `$currentObject/Attr` **inside** a `ContentParams` value on a `dynamictext` — bare or wrapped in a function, e.g. `ContentParams: [{1} = someFunction($currentObject/Attr, ...)]` or even `ContentParams: [{1} = $currentObject/Attr]` | **Drop the `$currentObject/` prefix — use the bare attribute name.** `ContentParams: [{1} = toString(Attr)]` or `ContentParams: [{1} = Attr]`. | 13 | Filter a `retrieve` by an association in a Retrieve object(s) activity: `retrieve $X from Module.Entity where AssocName = $Other` | **Fully module-qualify the association name in the WHERE clause**: `where "OwningModule"."AssocName" = $Other` | An unqualified association name in a retrieve XPath constraint compiles (`mxcli check` passes) and even loads in SP without a syntax error, but fails Studio Pro's own `mx check`/build with CE0161 "Error(s) in XPath constraint." | 15 | Quote attribute names inside a **`CHANGE`** activity argument list: `change $Obj ("State" = val)` | **STOP → never quote attribute names in CHANGE argument lists** | mxcli writes an invalid `AttributeIdentifier` to BSON — `StorageLoadException` on SP open, project unloadable. Confirmed 2026-07-20 on Mendix 11.12.0 / mxcli v0.13.0 (PROJECT-D): `change $Order ("State" = $MappedState, "StartDate" = [%CurrentDateTime%])` corrupted the MPR, required full backup restore. `mxcli check` and `mxcli check --references` both pass — only `mx check` / SP open reveals the damage. **Correct form:** `change $Order (State = $MappedState, StartDate = [%CurrentDateTime%])` — never quote attribute names in CHANGE value/expression positions. **Scope narrowed 2026-07-23:** originally written to cover `CREATE` too, but a PLM parts-flow project's `done-06-seed.mdl` (StyleGallery) has multiple `CREATE` activities with quoted attribute names (`"PLMId" = ...`, `"PartName" = ...`) that executed clean and gated `done-` (`mx check` 0 errors) — the confirmed corruption incident was CHANGE-specific, not CREATE. | 14 | `revoke Module.Role on Module.Entity (write *)` followed by `grant Module.Role on Module.Entity (write (list))`, when another role has its own separate `grant` on the same entity | **STOP → revoke ALL roles' access on the entity first, then re-grant every role's full rule in one script** | mxcli's revoke/grant on one role can collapse or silently merge the entity's access-rule set, dropping a *different* role's untouched grant entirely. Confirmed 2026-07-20 (PROJECT-D): revoking `write *` and re-granting an explicit write list for `TransportOperator` caused `TransportViewer`'s separate read-only grant to disappear, and `TransportOperator` silently lost its `create`/`delete` structural rights — surfacing as ~48 new CE2729 "no read access" errors on unrelated pages. Root cause only visible via `DESCRIBE ENTITY` after the fact — `mxcli check --references` and even a subsequent `mx check` pass to reveal the fallout, not the mechanism. **Safe pattern:** `revoke Role1 on Entity; revoke Role2 on Entity; grant Role1 on Entity (...); grant Role2 on Entity (...);` — rebuild the whole entity's security from scratch in one script whenever any existing rule needs its write/read list changed, never patch one role's rule in isolation. |
| 17 | Write a compound boolean expression combining uppercase `AND`/`OR` with a `!=` comparison anywhere in the same expression — in a Decision/IF condition OR a `retrieve ... where` clause | **Use lowercase `and`/`or` for boolean keyword operators.** Confirmed safe in every combination tested: lowercase `and`/`or` + `!=`, uppercase `AND`/`OR` + only `=` comparisons. Uppercase `AND` + a `!=`, and uppercase `OR` + a `!=`, both independently confirmed to fail — each tested directly, not inferred by symmetry from the other. Given the narrow, easy-to-miss trigger, default to lowercase `and`/`or` everywhere as a blanket-safe habit rather than trying to remember the exact boundary. | Confirmed 2026-07-23 (a PLM parts-flow project, mxcli v0.16.0) via 6 isolated tests, each run through a real `mx check` (not just `mxcli check`, which passes all of them): (1) `IF $Flag = Enum.HIGH AND $Outcome != Enum.ReleaseHold THEN` → CE0117. (4) Uppercase `AND` with two `=` comparisons (no `!=`) → 0 errors — isolates `!=` as the co-trigger, not `AND` alone. (5) Uppercase `OR` with two `=` comparisons → 0 errors. (6) Uppercase `OR` with one `=` and one `!=` comparison (`$Outcome = Enum.Release OR $Outcome != Enum.ReleaseHold`) → CE0117 — this is the one that was initially written up as assumed-by-symmetry rather than tested; it has since been run for real and does fail identically to the `AND` case. Same bug also reproduced in a `retrieve ... where PartId = 'x' AND PlantCode = $P AND "Status" != Enum.Archived` → CE0161; lowercase `and` fixed it. Root cause appears to be in mxcli's expression/XPath serializer mishandling the token sequence, not a real Mendix expression-language restriction (Studio Pro accepts lowercase `and`/`or` combined with `!=` without issue). |

| 19 | Write **any workflow MDL script** (CREATE WORKFLOW, ALTER WORKFLOW, or any script that adds user-task outcomes or call-microflow steps to an existing workflow) | See [[learned-workflow-patterns]] for the full syntax reference, warnings, and build order before scripting. **Read the BRD lifecycle section and wireframe for that feature BEFORE writing a single line.** Verify: (a) every user-task's allowed outcomes and their exact names, (b) which microflows belong inside which outcome branch vs unconditionally after the task, (c) whether a CALL MICROFLOW step is actually needed in MDL vs drag-and-drop in SP (prefer SP drag if it avoids the red-pin bug). Native `mx check` reports only the symptom (CE1613), not the damage. See [[learned-workflow-patterns]] §14 for the incident, the bisect procedure, and recovery. | Confirmed 2026-08-21 (a QA-sampling approval project, mxcli v0.18.0): a fix script called a `DEC_*` microflow that only ever existed in a superseded, never-executed script. CE1613 appeared a day later; creating the microflow cleared CE1613 but the workflow then failed `CE0495 "Duplicate name"` across 8 sibling activities the fix had never touched. Same defect class as BUG-92 (orphaned records surviving an edit, invisible to `DESCRIBE`). |
| 21 | `DROP` + `CREATE` (or `CREATE OR REPLACE`) any document **another script also edits** — an aggregator microflow, an after-startup chain, a navigation profile | **STOP → `describe` the live document first, diff your restatement against that dump, and name in the script header which call sites you preserved.** mxcli has no `ALTER MICROFLOW` for an existing body, and `ALTER NAVIGATION` **does not exist at all** (the parser rejects it: `no viable alternative at input 'alternavigation'`). Whole-document restatement is therefore the only write mxcli offers, which makes losing a sibling script's edit the *default* outcome, not an unlikely one. | Confirmed 2026-08-26 on a field run: two scripts each did DROP+CREATE on one shared seed aggregator. The second restated it as it had been *before* the first ran, and a demo-data seed call silently vanished. Every instrument was green — `mx check` reported **0 errors** because an uncalled microflow is perfectly legal, and `mxcli lint`'s orphan rule (QUAL004, `orphaned_elements.star`) exempts the `ACT_` prefix as a presumed UI entry point, so an `ACT_` microflow with no callers at all reports clean. It was found by opening a page and reading "0 to 0 of 0". |
| 22 | Write a script containing ANY non-idempotent statement — `alter entity … add attribute`, bare `CREATE ASSOCIATION`, bare `CREATE MICROFLOW`/`CREATE PAGE` on a name that may already exist | **STOP → use the `create or modify` form for every statement, and give every document exactly ONE owning script.** mxcli is **not transactional across statements**: the first failure stops the script and every statement below it is **silently skipped**, while the mxbuild gate reports 0 errors — the model is valid, it is merely missing work nobody asked it to skip. The property to hold is that `mdlsource/` replays cleanly against an EMPTY app; that is one command and it is the only thing that proves it. | Confirmed 2026-08-31 (a dashboard-publishing migration, mxcli v0.20.0). Script `09b` added two attributes with `alter entity … add attribute` and then defined two microflows. Re-running it after the attributes existed died on statement 1 with "attribute already exists" — and the two microflows at the end were never applied. It surfaced days later as `ACT_Version_Delete` quietly missing a call it had had an hour earlier, found by `DESCRIBE MICROFLOW` on a hunch; no gate saw it, because a microflow that no longer calls a sub-microflow is a perfectly valid model. Compounded by rule 21's defect one level up: six scripts held a grant on the same three entities, so whichever ran last decided their security. **The fix that makes both go away is the same one:** one owner per document, `create or modify` throughout, and a from-empty replay in CI or at wrap-up. Worked example incl. the before/after comparison: the project's `docs/REBUILD.md` pattern — 23/23 scripts replay, `BUILD SUCCEEDED`, rebuilt model identical to the live one element for element. |

**Default to mxcli for:** entities/attributes/enums, associations (after SHOW ASSOCIATIONS check), microflows (without inline assoc-sets), demo users, module roles/grants, navigation.

| 23 | Name any document or entity that **might already exist** — `create or modify` on an entity, or any `create or replace` on a page, layout or microflow | **STOP → run `mxcli diff -p <app>.mpr <script>.mdl --format struct` FIRST.** It is read-only, it takes a second, and it prints exactly what the script would add and what it would REMOVE. Read the `-` lines before you exec, every time. Rules 21 and 22 tell you to write `create or modify` and to give each document one owner; this is the check that the name you chose is actually free. | Confirmed 2026-09-01 (a dashboard-publishing migration, mxcli v0.20.0). A new script declared `create or modify non-persistent entity DashboardPublishing."ViewerContext"` with one attribute, believing the name unused. The entity already existed, owned by an earlier page script, carrying four attributes — `VersionLabel`, `HasContent`, `Html`, `DashboardTitle` — which are the entire datasource of the app's viewing page. `diff --format struct` reported `+ Attribute SharedCount` and **four `- Attribute` lines**, i.e. `create or modify` on an entity does not merge into the attribute set, it **replaces** it. Renaming the new entity took ten seconds; the alternative was a page that renders nothing, on a model that would have passed `mx check` and mxbuild clean, since an entity losing four attributes is a perfectly valid model. **This is the cheapest guard in the file — the whole rule is `diff` before `exec`.** |

## MDL gotchas (quick reference — common traps)

These don't require a STOP, but will cause silent failures or check errors if missed:

- **`DROP MODULE` leaves the module's on-disk folders behind, and its CSS entirely intact.** The model loses the module; `themesource/<Module>/`, `skillssource/_modules/<module>/` and `javascriptsource/<module>/` stay as empty directories, and **every line of `theme/web/*.scss` is untouched** because that is app-level, not module-scoped. The empty folders are cosmetic — remove them after the drop, never before, and only after `find <dir> -type f` prints nothing. The surviving CSS is not cosmetic: see [[learned-stylegallery]] → "The Mendix DOM contract". A reset that wiped the model and left the stylesheet is a half-reset that looks total.

- **Quote / unquote retry rule — when any identifier fails, immediately try the other form:** If a script with quoted identifiers (`"Name"`) fails at `mxcli check`, `mx check`, or runtime, try removing the quotes. If an unquoted form fails, try adding quotes. Never file a blocker or conclude it's impossible before trying both. This applies to every identifier position: microflow names, parameter names, entity names, attribute names, association names, page names. One form will always work; the other may silently produce wrong BSON or a parse error.

- **CALL MICROFLOW WITH clause in workflows — mxcli v0.16.0 bug — use SP:** The `WITH (Module.MF.Param = '$workflowContext')` syntax parses clean (`mxcli check` passes) but always writes a null `ParameterId` to BSON, causing `mx check` to crash with `set_ParameterId ArgumentNullException`. Confirmed across multiple quote/unquote variants. The parameter binding for workflow CALL MICROFLOW steps **must be set in Studio Pro** (double-click the activity → map parameter manually). Do not attempt to script WITH clauses for workflow CALL MICROFLOW steps in mxcli v0.16.0.

- **Never quote attribute paths on ANY variable, not just `$currentUser`:** write `$currentUser/Name` and `$Param/ResolutionNote`, never `$currentUser/"Name"` or `$Param/"ResolutionNote"`. The quoted form is syntactically valid MDL so `mxcli check` passes, but SP/`mx check` rejects it at load/build time with CE0117 ("Error(s) in expression"). Confirmed 2026-07-20 across `$currentUser/"Name"` (three TransportEvent CREATE activities) AND `$RetryInput/"ResolutionNote"` (a NPE parameter, two activities in a different microflow) — this is a general variable-attribute-traversal rule, not a `$currentUser`-specific quirk. Only quote the attribute when it conflicts with an MDL reserved word, never as a blanket safety measure.

- **Grants belong co-located with the element — never deferred to a single security script:** write `grant execute` at the end of the microflow script that creates the microflow; `grant view` at the end of the page script; entity access grants at the end of the domain script. A deferred `security.mdl` that does all grants at once is the primary cause of silently inaccessible pages and microflows — mxbuild produces no CE error for a missing grant, so the only signal is a blank screen at runtime. A `roles.mdl` script for module/user role *creation* is fine; it must not carry grants. **The entity and its access rule are one unit — create both in the same script, same commit.** Confirmed incident: a module shipped with entities created and used across several microflows/pages before any entity access rule existed for them — `mx check` never flags a missing access rule, so it surfaced only as CE2729 ("no read access") once a role without Administrator rights opened the page. The same incident also showed a module role created but never mapped to any user role: the page rendered with zero visible content, no error at all, because nothing failed — the widgets were just invisible to that user's role. **A "ready-check" must mean built, not decided** — writing down that a role/entity/rule *should* exist is not the same claim as it existing; verify with `DESCRIBE ENTITY`/`SHOW GRANTS`, not by re-reading your own plan. Pre-flight, before writing any entity: (1) does this entity get an access rule in the same script? (2) does every module role that should see it exist and get granted? (3) is every module role actually composed into the user role(s) that need it? (4) for non-persistent DTOs, do they need create/delete grants at all, or only read/write (see lint rule CONV006)?
- **All grants — module roles are module-scoped (entities, microflows, pages):** the role in any `GRANT` must be declared *inside the same module as the element being granted*. This applies equally to entity access, microflow execute, and page view grants. Referencing `ModuleA.SomeRole` in a grant on any `ModuleB` element produces a CE error ("role not found in module"). Every module that owns grantable elements must declare its own module roles. User roles then *compose* module roles from all relevant modules:
  ```
  -- Each module declares its own roles
  create module role "ModuleB"."ReadRole";
  -- All three grant types use same-module roles only
  grant entity access on "ModuleB"."Widget" to "ModuleB"."ReadRole" (read: all);
  grant execute on microflow "ModuleB"."ACT_DoThing" to "ModuleB"."ReadRole";
  grant view on page "ModuleB"."Overview" to "ModuleB"."ReadRole";
  -- User roles compose across modules
  create user role "AppUser" ("System"."User", "ModuleA"."ReadRole", "ModuleB"."ReadRole");
  ```
  Anti-pattern to watch for: a single `security-setup.mdl` that uses a shared `Security.UserRole` to grant access to elements from three other modules — that will fail CE on every element outside `Security`.
- **Demo user passwords — never touch MxAdmin, never set passwords:** MxAdmin ships in every project with password `1`; do not wipe, reset, or re-create it. Demo users are created by name + role only — no password block. The user switches to a demo account inside the app from MxAdmin; no password is needed. Pattern: `create demo user "firstname.lastname" with roles "Module"."Role";` — nothing more.
- **`System.User` missing from user roles:** every user role must include `System.User` — without it, users cannot log in. mxbuild passes, SP loads clean, no CE errors — silent login failure only. Pattern: `create user role "MyRole" ("System"."User", "Module"."Role", ...)`. Applies to every user role, no exceptions.
- **Keyword collisions:** widget/element names must not match MDL/OQL reserved words (case-insensitive): `MIN`, `MAX`, `IN`, `OUT`, `COUNT`, `SUM`, `AVG`, `ROW`, `COLUMN`, `STATUS`, etc. Use descriptive names or double-quote them. Confirmed 2026-07-23 (a PLM parts-flow project): a bare `Status` attribute name inside a `retrieve ... where` clause (`where ... and Status != Enum.Value`) compiled fine through `mxcli check` but failed a real `mx check` with CE0161 "Error(s) in XPath constraint" — quoting it (`"Status" != Enum.Value`) fixed it. This is consistent with the entity's own domain model already quoting `"Status"` specifically in its access-rule read lists (all its sibling attributes unquoted) — a signal worth checking for before assuming a reserved-word conflict is the cause of a CE0161.
- **Enumeration values named with reserved words cannot be targeted by `alter enumeration ... modify value`:** the statement fails to parse when the value NAME collides with an MDL reserved word (confirmed by direct test on `Receive`, `Move`, `Count`, `Open` in one enum set — a WMS demo project, Mendix 11.12.0, 2026-07-29), and **double-quoting does not help in that grammar position**. Workaround: use the declaration form `create or modify enumeration`, which does honour quoting — but ⚠️ it *replaces* the enumeration, so restate the FULL value set (a delta drops the rest) and carry over the original doc comment. Related trap: only ever change the *caption*; renaming a value NAME silently breaks every microflow/XPath/page reference and `mxcli check` will not catch it.
- **`EXTENDS` placement:** goes **before** the opening paren: `CREATE PERSISTENT ENTITY Mod.Photo EXTENDS System.Image (...)` — not after.
- **No `CASE/WHEN`:** use nested `IF/ELSE`. No `TRY/CATCH`: use `ON ERROR { ... }`.
- **Enum in string context:** always `toString($Obj/EnumAttr)` — never use the enum attribute directly where a String is expected.
- **`$Obj/AttrName` not `$Obj/"AttrName"`:** quoting attribute names in path expressions passes `mxcli check` but produces CE0117 at mxbuild. Quotes are correct for identifiers in declarations; wrong for path traversal.
- **Cross-module association expression paths:** for navigation through a cross-module association to a nested attribute, the entity name must be included: `$Item/ModuleA.Item_Other/ModuleB.OtherEntity/Attr` not `$Item/ModuleA.Item_Other/Attr`. The short form silently compiles but SP rejects it (CE0117). A bare `= empty` check does NOT need the long form.
- **`mxcli check` does not catch corruption:** it validates MDL grammar only. Items 1–11 above are all semantically valid MDL that check passes — only mxbuild or SP open will reveal the damage. Always run the real mxbuild gate after exec (see `iterative-build-loop.md`).
- **No `elseif` in page/widget expressions (DynamicClasses, Visible, ContentParams, etc.) — nest `if ... then ... else if ... then ... else ...` instead:** microflow `IF/ELSEIF/ELSE` statements are compiled by mxcli into nested decision-split activities, so `elseif` works fine there. But a raw expression string handed to a page widget property (e.g. `DynamicClasses: 'if $Obj/A = false then ''x'' elseif $Obj/B then ''y'' else ''z'''`) is passed through to Mendix's native expression parser mostly as-is, which has no single `elseif` token — it produces CE0117 ("Error(s) in expression.") at native `mx check`, invisible to `mxcli check --references`. Confirmed 2026-08-13, PROJECT-F: unquoting the attribute paths in the same expression did NOT fix it (ruled out as the same family as the quoting bugs above) — only replacing `elseif` with nested `else if` did. Applies to any multi-branch conditional written directly into a page/snippet widget property, not just DynamicClasses.

## Final self-check (mandatory before reporting back)

After drafting a script, re-read it line by line against the table above — not just the mental pre-check you did before writing. Inline assoc-sets, conditional visibility inside datagrid customContent columns, and cross-module association traversals as widget datasources can creep in during drafting without intent. `mxcli check --references` will not catch them. This re-read is the actual corruption-prevention step.

**Then diff it before you exec it** (rule 23): `mxcli diff -p <app>.mpr <script>.mdl --format struct` is read-only and prints what the script would add *and remove*. The re-read above catches what you wrote; the diff catches what you did not know was already there — a name you believed free, an entity whose attribute set your `create or modify` would replace rather than extend. Read every `-` line.

**And check the size before you execute:** could you diagnose a failure of this script from the
error output alone, or would you be re-reading the whole file to find which unit broke? If the
latter, split it and say so in chat before executing — even when the build plan handed it to
you whole. A per-layer plan does not mean a layer is one script; see
`brd-to-build-plan.md` Step 3. Observed failure: a plan that put 13 microflows in one exec.

Isolate anything the other units depend on, group the rest by "would one failure explain the
others?", and do not over-split — every extra script is another approval prompt, and approval
fatigue hollows out RULE 1 as surely as an opaque mega-script does.
