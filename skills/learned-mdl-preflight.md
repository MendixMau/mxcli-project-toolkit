# MDL Pre-flight Checklist — STOP conditions before writing any script
**Applies to:** any mxcli project.
**Purpose:** Before drafting any MDL script, check every planned operation against this table. Each STOP row was born from a real MPR corruption or silent runtime failure — not theoretical concerns. Skipping this check has caused project-unloadable corruption every time.

**Source:** Generalized from a live Mendix 11.12.0 Beta project, 2026-07-06/07. Incident detail stays in that project's own `bug-logs/` — only the generalizable rule is here.

**Version context:** Rules marked "STOP" were confirmed on specific mxcli/Mendix versions noted per entry. Rules 1b and 10 were retested 2026-07-09 on mxcli v0.13.0 / Mendix 11.12.0 and confirmed resolved. Rule 9 was retested 2026-07-09 via `mxcli --mcp` on v0.13.0 and confirmed resolved (BSON serialization bug only affects the disk write path; `--mcp` bypasses it entirely). If in doubt, retest on your version and stamp the result in `bug-logs/mxcli-bugs.md`.

**v0.20.0 deltas (retested 2026-08-31, [bug-logs/mxlabs-v0.20.0-retest-2026-08-31.md](../bug-logs/mxlabs-v0.20.0-retest-2026-08-31.md)) — on a project whose mxcli is ≥ v0.20.0:**
- **Rule 17 (uppercase `AND`/`OR` + `!=`) is resolved** — builds at 0 errors; keep the lowercase habit only for projects pinned to older binaries.
- **Rule 1c's class (ALTER PAGE `SET Editable`/conditional settings) is resolved** — `SET Editable = [expr] ON widget` stores correctly and the project loads.
- **ALTER PAGE now requires the braced block form** `ALTER PAGE Mod.Page { SET … ON w; };` — the old flat `alter page X set … on w;` is a parse error. DataGrid2 columns are addressed by **derived** name (bound attribute, else caption — MDL-WIDGET16), and a bare column name in REPLACE is refused in favour of `grid.column`.
- **Still corrupting, STOP stays:** workflow `DECISION` activities (BUG-76 — project unloadable, `EnumerationValueIdentifier`).
- ~~`marketplace install` on a split-model project (#879)~~ — **RESOLVED in v0.21.0, STOP LIFTED (probed 2026-09-10).** Install no longer shells out to `mx module-import`; it copies units with mxcli's own writer and MPR v2 survives. The destructive path is now opt-in behind `--allow-format-change`, so the failure can only happen on purpose. Measured on a real 501-unit project: 501 → 1075 `.mxunit`, `.mpr` 84 KB → 156 KB (an index, not the 35 MB blob #879 produced), native mxbuild **0 errors**. **Read `bug-logs/mxcli-bugs.md` → the #879 entry before your first install** — the corruption is gone, and three *new* operational traps replaced it (packages do not carry their dependencies; two `mxcli fix` repairs are mandatory, not advisory; a bundled widget can silently fail to land and the installer cannot self-repair it).
- The 10–12-writes-per-session cap from BUG-97 is downgraded to snapshot-plus-read-back: 16 sequential writes were clean on v0.20.0.
- **Rule 2 (settings/security-level writes) is resolved** — probe-verified 2026-08-31: `alter project security level production`, `alter project security demo users on`, `alter project security guest access off` (guest access is new v0.19 surface — anonymous access was previously read-only), `alter settings model FirstDayOfWeek = Monday` and `alter settings configuration … HttpPortNumber` all land, read back, and cold-load at 0 errors. **Project security setup is now a scriptable project-start step, not an end-of-build Studio Pro chore** — see `brd-to-build-plan.md` Step 5's scaffold row.

## Step 0 — choose the write mode (do this first, before the STOP table)

There are three write modes, and they are **co-equal tools chosen by the shape of the work** — not one default plus two fallbacks. Pick the mode from the task first; *then* use the STOP table below only as the safety overlay that overrides your pick for the handful of operations mxcli corrupts. "CLI unless forced to MCP" is the wrong mental model — it is why projects drift to CLI-only and never touch the live-editing loop.

| Mode | Command | Reach for it when | SP |
|---|---|---|---|
| **CLI** (disk write) | `./mxcli exec script.mdl` | Bulk, structural, done-once: a whole domain model, a module's microflows, access rules, navigation, demo users. One script scaffolds a lot. | Closed |
| **MCP + MDL** | `./mxcli --mcp http://localhost/mcp --mcp-dial localhost:7782 exec script.mdl` | Iterative refinement and UI tuning where restarting SP per change would kill flow — page layout, widget wiring, visibility expressions. Live edit, no recompile wait. Also the required path for rule 9 (inline assoc-sets). | Open |
| **Hand-rolled MCP** | `pg_patch_page`, `ped_create_document`, `ped_update_document` | Widget JSON shapes MDL has no syntax for — rules 1, 6, 6b, 7 and datagrid customContent conditionals. Confirmed payloads in `learned-mcp-patterns.md`. | Open |

**Typical module rhythm:** one CLI exec to scaffold domain + microflows → MCP+MDL for page iteration and UI tweaks → hand-rolled MCP only for the specific widget shapes MDL can't reach. A project that only ever runs CLI is usually leaving the fast UI-iteration loop on the table, not being more disciplined.

**When more than one mode genuinely works** — most page changes and most single/small microflow builds fall in this zone — don't silently pick one. Name the viable modes (CLI / MCP+MDL / hand-rolled MCP — remember MCP splits into these two: MDL run through the MCP connection, or direct `pg_patch_page`/`ped_*` calls with no MDL at all), give a one-line recommendation with reason (e.g. "MCP+MDL, since SP is already open and this is a small widget tweak" / "CLI, this is a whole-module scaffold"), and let the user pick before executing. Only skip asking when the STOP table forces a mode, or the user has already stated a standing preference for that exact operation type in this session/project. Default lean, absent other signal: MCP for page edits and small microflow builds, CLI for bulk/structural work (domain models, access rules, navigation, demo data).

Once you've picked a mode per operation, run the STOP table below against every one of them — it overrides your pick whenever an operation falls in the corrupting set.

**Also decide, per document, where it lands.** Any operation that *creates* a document — page, snippet, microflow, nanoflow — needs its folder chosen now and written into the `folder` property of the same statement, not fixed afterwards. Read the path off the brief's `### Document folder plan`; when there is no row for it, derive it per `module-folder-convention.md` ("Deciding the path"), and escalate rather than guess when the feature group is unclear. Omitting `folder` is legal MDL that silently drops the document at module root — no error, no gate, and a cleanup job later that nobody schedules.

**Companion skills:** `learned-mcp-patterns.md` (MCP alternatives), `bug-logs/mxcli-bugs.md` (bug detail), `iterative-build-loop.md` (exec discipline), `learned-microflow-patterns.md` (annotation + inline assoc rules)

## The checklist — run before writing a single line of MDL

| # | If your script will… | Then… | Root cause |
|---|---|---|---|
| 1 | Use `visible:` or `editable:` **conditional expressions** on containers **inside a `datagrid customContent` column** | **STOP → MCP** (`pg_patch_page`) | mxcli writes blank `AttributeIdentifier` → `StorageLoadException` on SP open. **BUG-18, still open on v0.13.0** (found 2026-07-03 after v0.13.0 release). **Primary real-world trigger: per-value badge pattern** — multiple containers with `Visible: [State = ENUM.Value]` inside a column. mxbuild passes clean; SP load fails. Safe CLI alternative: `dynamictext (Attribute: "State")` renders enum caption natively. Do NOT use `ContentParams: [{1} = toString("State")]` inside customContent — resolves as attribute path → CE1613. Per-value colours require `pg_patch_page` MCP. |
| 1b | Use `visible:` or `editable:` conditional expressions on **regular widgets / dataview / page-level containers** in a `CREATE PAGE` or `CREATE SNIPPET` statement | Safe on mxcli v0.13.0 — retested 2026-07-09 on a large-source WMS project (Mendix 11.12.0), 0 mxbuild errors. Fixed by codec engine (#627). **Use mxcli.** | Was: STOP in pre-v0.13.0; no longer applies to regular widgets in CREATE. |
| 1c | Use `ALTER PAGE { SET Visible = '...' ON widgetName }` to add/change a **conditional visibility expression** on an existing widget | **STOP → Studio Pro GUI** | `ALTER PAGE SET Visible` writes a blank `AttributeIdentifier` on the `ConditionalVisibilitySettings` → `StorageLoadException` on SP open. Confirmed 2026-07-20 on Mendix 11.12.0 / mxcli v0.13.0 (PROJECT-D). Note: Rule 1b (CREATE PAGE with Visible) is safe; only the ALTER path is broken. **Recovery:** `./mxcli -p PROJECT-D.mpr -c "ALTER PAGE Mod.Page { SET Visible = '' ON widgetName }"` clears the bad value, then set the expression via SP. |
| 2 | Call `alter settings configuration`, `alter settings model`, or `alter project security level` | **RESOLVED in mxcli v0.20.0 — verified 2026-09-01 (`tests/retests/retest-bug22-settings-writes.sh`, 18 executions, 0 errors) and re-confirmed 2026-08-31 by a second harness. Use mxcli directly.** | Was BUG-22: BSON stream-desync on the Settings unit, mxcli v0.13.0. Real on binaries < v0.20.0 — projects pinned there keep the old STOP → Studio Pro GUI. Full retest record: `bug-logs/mxlabs-v0.20.0-retest-2026-08-31.md`. |
| 3 | Drop an attribute that has security grants applied to it | **STOP → Studio Pro GUI** | mxcli removes the attribute but leaves dead UUID pointers in the entity access rules → `KeyNotFoundException` on load (BUG-01) |
| 4 | Bind a widget to `AutoChangedBy` or `AutoChangedDate` system attributes | **STOP → omit or MCP** | Produces CE1613 dangling reference — these attributes are not bindable via mxcli widget expressions |
| 5 | Pass scalar (non-entity) parameters from a page button to a microflow | **STOP → redesign** | Mendix platform constraint: page buttons can only pass entity objects to microflows, never individual String/Integer/Decimal values. Silently fails to bind (CE1571). The microflow must take the whole object. |
| 6 | Use a COMBOBOX widget in association mode | **STOP → MCP** (`pg_patch_page`) | mxcli rejects the `Entity` property required by SP (MDL-WIDGET01), SP requires it (CE0642) — no working mxcli path exists |
| 6b | Use `DatagridDropdownFilter` in association (ref) mode as a DataGrid2 filter | **STOP → MCP** (`pg_patch_page`) | Confirmed working JSON pattern exists — see `learned-mcp-patterns.md`. `refOptions` microflow must be no-param; use `DomainModels$IndirectEntityRef` for `refEntity`; use `Pages$MicroflowSource` (not `CustomWidgets$CustomWidgetMicroflowSource`) |
| 7 | Use a cross-module association traversal as a widget datasource (`$currentObject/OtherModule.Assoc`) in DataGrid/DataView/ListView | **RESOLVED in mxcli v0.17.0 — verified 2026-08-11 (BUG-20/#854). Use mxcli.** Projects pinned to v0.16.0 keep **STOP → MCP** (`pg_patch_page`). | Was: mxcli wrote a null `DestinationEntityId` on the `EntityRefStep` → `StorageLoadException` on SP open. Same-module traversals were always fine. |
| 8 | Create any association — same- or cross-module | **STOP → run `SHOW ASSOCIATIONS` first** | No `IF NOT EXISTS` support — re-running a CREATE silently duplicates the association; mxbuild then flags CE0065/CE0069. Only write `CREATE ASSOCIATION` for names that do not yet appear in `SHOW ASSOCIATIONS` output. |
| 9 | Set an association inline in a CHANGE or CREATE activity: `change $Obj (Module.AssocName = $Other)` or `create Entity (Module.AssocName = $Other)` | **RESOLVED in mxcli v0.17.0 for the cross-module case — verified 2026-08-11** (see `bug-logs/mxcli-bugs.md` BUG-21/#838): v0.17.0 either rejects an unresolvable association name with a clear pre-write error, or writes it correctly with no corruption. Retire the `--mcp` requirement below for projects whose `./mxcli` binary has been upgraded to v0.17.0+; keep it in force for any project still pinned to v0.16.0. **Depends on whether the association crosses modules — check this before picking a mode.** **Cross-module (e.g. to `System.User`, `Administration.Account`, or any other module's entity): STOP → `mxcli --mcp exec script.mdl`** (SP must be open) — confirmed still corrupting on **v0.16.0** as recently as 2026-07-13 (`change $NewAccount (System.User_UserRoles = $Role)` → invalid-`AttributeIdentifier` load failure, a WMS conversion project, two branches). **Same-module (both entities in the association live in the same module — including a marketplace module's own internal associations, not just a project-authored module): confirmed SAFE via plain CLI on v0.16.0**, 2026-07-23 (a PLM parts-flow project) — an isolated throwaway test (2 new entities + 1 new association, all in one project module) and a real 176-activity production microflow (46 inline association-sets, all within the same module) both passed a full `mx check` clean. Do not assume this same-module finding extends to cross-module cases — those two are separately confirmed, in opposite directions, on the identical mxcli version. When genuinely unsure which category an association falls into, treat it as cross-module (the safer default) until confirmed otherwise. **⛔ Never resolve this STOP by dropping the association set** — the object still needs the link. Routing to `--mcp` (or MCP fallback) preserves it; silently omitting it ships a broken golden path (a real WMS incident: a scanned order created with no link to its unit/location, mxbuild clean). If the brief's golden-path data-effects table lists an association for this action, it must be set. | mxcli's disk-write serializer writes the association name as an `AttributeIdentifier` in CHANGE/CREATE BSON in a way that fails module-boundary resolution on SP load for cross-module associations specifically — same-module associations apparently resolve fine through the same code path. `--mcp` routes through SP's own engine, bypassing mxcli's serializer entirely, and is confirmed safe for both cases. **Reading through an association (`$Obj/Module.Assoc/Target/Attr`) is safe on any path, cross-module or not.** |
| 10 | Use `count($list)` anywhere in an expression | **Write `length($list)`.** | `count()` is not a Mendix expression function: `toString(count($X))` passes `mxcli check` and fails `mx check`/SP with CE0117 (2026-07-20). The 2026-07-09 "count() is safe" retest is unverified — prefer `length()` until re-confirmed. |
| 11 | Filter an XPath with an association-traversal as the comparand: `[Assoc_X = $Ctx/Other.Assoc]` | **STOP → retrieve target first, then filter** | XPath constraint right-hand side must be a directly-bound variable, not an association path. Pattern: `retrieve $Target from ... where [...]; retrieve $Result from Module.Entity where [Module.Assoc_X = $Target]` |
| 12 | Write `$currentObject/Attr` **inside** a `ContentParams` value on a `dynamictext` — bare or wrapped in a function, e.g. `ContentParams: [{1} = someFunction($currentObject/Attr, ...)]` or even `ContentParams: [{1} = $currentObject/Attr]` | **Drop the `$currentObject/` prefix — use the bare attribute name.** `ContentParams: [{1} = toString(Attr)]` or `ContentParams: [{1} = Attr]`. Function calls themselves are fine; the prefix is the trigger. | mxcli serializes the whole ContentParams value as an attribute-path suffix and concatenates the dataview's qualified entity name onto it — producing a nonsense path, CE1613: "The selected attribute '<Entity>.<literal expression text>' no longer exists." Confirmed on Mendix 11.12.0 / mxcli v0.13.0, 2026-07-16 and re-confirmed 2026-07-20 (root cause corrected — see BUG-23): the trigger is the literal `$currentObject/` prefix, not "any function call" as originally written here, and it fails even with NO function at all (bare `$currentObject/Attr`). **`Attribute: "AttrName"` is NOT a safe alternative for non-string types** — mxcli silently re-serializes it back into the same broken `ContentParams: [{1} = toString($currentObject/Attr)]` form (confirmed via `describe page`), so it round-trips into this exact bug. **Do not confuse with `DynamicClasses`/`Visible` expressions, which take the opposite form and genuinely require `$currentObject/Attr`** — e.g. `DynamicClasses: 'if $currentObject/State = Enum.Value then ...'` is correct and already the working pattern elsewhere in this codebase. `mxcli check`/`describe page` never catch this — only a real `mx check`/`docker check`/SP compile does. |
| 13 | Filter a `retrieve` by an association in a Retrieve object(s) activity: `retrieve $X from Module.Entity where AssocName = $Other` | **Fully module-qualify the association name in the WHERE clause**: `where "OwningModule"."AssocName" = $Other` | An unqualified association name in a retrieve XPath constraint compiles (`mxcli check` passes) and even loads in SP without a syntax error, but fails Studio Pro's own `mx check`/build with CE0161 "Error(s) in XPath constraint." Confirmed 2026-07-20 on Mendix 11.12.0 (PROJECT-D): two retrieves using the bare association name (`TransportOrder_TransportUnit`, `TransportOrder_TargetLocation`) both failed; a third retrieve in the same microflow that already used the fully qualified form (`Transportation.TransportOrder_TransportUnit`) passed clean. `mxcli check --references` does not catch this — only `mx check` / SP does. |
| 15 | Quote attribute names inside a **`CHANGE`** activity argument list: `change $Obj ("State" = val)` | **STOP → never quote attribute names in CHANGE argument lists** | mxcli writes an invalid `AttributeIdentifier` to BSON — `StorageLoadException` on SP open, project unloadable. Confirmed 2026-07-20 on Mendix 11.12.0 / mxcli v0.13.0 (PROJECT-D): `change $Order ("State" = $MappedState, "StartDate" = [%CurrentDateTime%])` corrupted the MPR, required full backup restore. `mxcli check` and `mxcli check --references` both pass — only `mx check` / SP open reveals the damage. **Correct form:** `change $Order (State = $MappedState, StartDate = [%CurrentDateTime%])` — never quote attribute names in CHANGE value/expression positions. **Scope narrowed 2026-07-23:** originally written to cover `CREATE` too, but a PLM parts-flow project's `done-06-seed.mdl` (StyleGallery) has multiple `CREATE` activities with quoted attribute names (`"PLMId" = ...`, `"PartName" = ...`) that executed clean and gated `done-` (`mx check` 0 errors) — the confirmed corruption incident was CHANGE-specific, not CREATE. Quoting attribute names in `CREATE` argument lists is safe; only `CHANGE` is a STOP. |
| 14 | `revoke Module.Role on Module.Entity (write *)` followed by `grant Module.Role on Module.Entity (write (list))`, when another role has its own separate `grant` on the same entity | **STOP → revoke ALL roles' access on the entity first, then re-grant every role's full rule in one script** | mxcli's revoke/grant on one role can collapse or silently merge the entity's access-rule set, dropping a *different* role's untouched grant entirely. Confirmed 2026-07-20 (PROJECT-D): revoking `write *` and re-granting an explicit write list for `TransportOperator` caused `TransportViewer`'s separate read-only grant to disappear, and `TransportOperator` silently lost its `create`/`delete` structural rights — surfacing as ~48 new CE2729 "no read access" errors on unrelated pages. Root cause only visible via `DESCRIBE ENTITY` after the fact — `mxcli check --references` and even a subsequent `mx check` pass to reveal the fallout, not the mechanism. **Safe pattern:** `revoke Role1 on Entity; revoke Role2 on Entity; grant Role1 on Entity (...); grant Role2 on Entity (...);` — rebuild the whole entity's security from scratch in one script whenever any existing rule needs its write/read list changed, never patch one role's rule in isolation. |
| 17 | Write a compound boolean expression combining uppercase `AND`/`OR` with a `!=` comparison anywhere in the same expression — in a Decision/IF condition OR a `retrieve ... where` clause | **Use lowercase `and`/`or` for boolean keyword operators.** Confirmed safe in every combination tested: lowercase `and`/`or` + `!=`, uppercase `AND`/`OR` + only `=` comparisons. Uppercase `AND` + a `!=`, and uppercase `OR` + a `!=`, both independently confirmed to fail — each tested directly, not inferred by symmetry from the other. Given the narrow, easy-to-miss trigger, default to lowercase `and`/`or` everywhere as a blanket-safe habit rather than trying to remember the exact boundary. | Confirmed 2026-07-23 (a PLM parts-flow project, mxcli v0.16.0) via 6 isolated tests, each run through a real `mx check` (not just `mxcli check`, which passes all of them): (1) `IF $Flag = Enum.HIGH AND $Outcome != Enum.ReleaseHold THEN` → CE0117. (2) Same with explicit parens per comparison → still CE0117; parens are not the fix. (3) Same with lowercase `and` → 0 errors. (4) Uppercase `AND` with two `=` comparisons (no `!=`) → 0 errors — isolates `!=` as the co-trigger, not `AND` alone. (5) Uppercase `OR` with two `=` comparisons → 0 errors. (6) Uppercase `OR` with one `=` and one `!=` comparison (`$Outcome = Enum.Release OR $Outcome != Enum.ReleaseHold`) → CE0117 — this is the one that was initially written up as assumed-by-symmetry rather than tested; it has since been run for real and does fail identically to the `AND` case. Same bug also reproduced in a `retrieve ... where PartId = 'x' AND PlantCode = $P AND "Status" != Enum.Archived` → CE0161; lowercase `and` fixed it. Root cause appears to be in mxcli's expression/XPath serializer mishandling the token sequence, not a real Mendix expression-language restriction (Studio Pro accepts lowercase `and`/`or` combined with `!=` without issue). |
| 18 | Write **any workflow MDL** — `CREATE`/`ALTER WORKFLOW`, a `CALL MICROFLOW` step, a `JUMP TO`, user-task outcomes | **STOP → read [[learned-workflow-patterns]] first, then script.** The rules that used to sit here as rows 18–20 and 24 live there: `WITH` mapping for every callee parameter (§7/§13 — red-pin corruption, invisible to `mxcli check`); every callee's `create/modify microflow` above the workflow statement in the same exec (§14 — an unknown callee corrupts the stored workflow, and creating it afterwards does not heal it); `JUMP TO` targets are the real activity names, never the `DESCRIBE` output's (§21, BUG-109, mxcli#1005); read the BRD lifecycle + wireframe before writing a single outcome. | Four incidents, four projects (2026-07-24 PLM parts-flow ×2, 2026-08-21 QA-sampling approval, 2026-08-31 BPM-engine conversion) — all passed `mxcli check --references` and `exec`, all failed only on SP open or native `mx check`. |
| 16 | Write an access-rule XPath constraint with a **path expression inside the `[%CurrentUser/...%]` substitution token** — `[Assoc = '[%CurrentUser/Module.OtherAssoc%]']`, especially crossing module boundaries | **Never put a path inside the CurrentUser substitution. Keep it bare (`'[%CurrentUser%]'`) and do the ENTIRE multi-hop/cross-module traversal on the left-hand side instead**, qualifying the entity name at every module crossing (same rule as the "cross-module association expression paths" MDL gotcha, extended here to access-rule XPath constraints, not just microflow expressions). Was: `[FeasibilityDecision_Supplier = '[%CurrentUser/PLM.Account_Supplier%]']`. **Fix (confirmed working):** `[PLM.FeasibilityDecision_Supplier/PLM.Supplier/Administration.Account_Supplier = '[%CurrentUser%]']` — walk Supplier→Account fully on the left, compare directly to the (already-an-Account) CurrentUser token. | This is genuinely invalid Mendix XPath, not an mxcli-specific bug — `CE0161` "Error(s) in XPath constraint" is Mendix correctly rejecting it every time it's checked, which is why it kept resurfacing across three separate incidents on a PLM parts-flow project (2026-07-22/23, `bug-logs/mxcli-bugs.md`) that were originally misdiagnosed as mxcli corrupting the domain model on unrelated grant rewrites. In fact the "unrelated entity broke too" symptom was just two independently-broken rules (both using the same invalid CurrentUser-path form) surfacing together once a full `mx check` ran — not one rule corrupting the other. Once rewritten to the correct bare-CurrentUser/full-LHS-chain form, the earlier "Studio Pro GUI only, module-wide" restriction no longer applies — **confirmed mxcli-safe 2026-07-23** via `test-05-currentuser-xpath-chain.mdl` (rebuilt all 4 role grants on the affected entity through mxcli exec, reproducing the corrected XPath verbatim, `mx check: 0 errors`). Use mxcli directly for this pattern; no GUI fallback needed. |
| 21 | `DROP` + `CREATE` (or `CREATE OR REPLACE`) any document **another script also edits** — an aggregator microflow, an after-startup chain, a navigation profile | **STOP → `describe` the live document first, diff your restatement against that dump, and name in the script header which call sites you preserved.** mxcli has no `ALTER MICROFLOW` for an existing body, and `ALTER NAVIGATION` **does not exist at all** (the parser rejects it: `no viable alternative at input 'alternavigation'`). Whole-document restatement is therefore the only write mxcli offers, which makes losing a sibling script's edit the *default* outcome, not an unlikely one. | Confirmed 2026-08-26 on a field run: two scripts each did DROP+CREATE on one shared seed aggregator. The second restated it as it had been *before* the first ran, and a demo-data seed call silently vanished. Every instrument was green — `mx check` reported **0 errors** because an uncalled microflow is perfectly legal, and `mxcli lint`'s orphan rule (QUAL004, `orphaned_elements.star`) exempts the `ACT_` prefix as a presumed UI entry point, so an `ACT_` microflow with no callers at all reports clean. It was found by opening a page and reading "0 to 0 of 0". |
| 22 | Write a script containing ANY non-idempotent statement — `alter entity … add attribute`, bare `CREATE ASSOCIATION`, bare `CREATE MICROFLOW`/`CREATE PAGE` on a name that may already exist | **STOP → use the `create or modify` form for every statement, and give every document exactly ONE owning script.** mxcli is **not transactional across statements**: the first failure stops the script and every statement below it is **silently skipped**, while the mxbuild gate reports 0 errors — the model is valid, it is merely missing work nobody asked it to skip. The property to hold is that `mdlsource/` replays cleanly against an EMPTY app; that is one command and it is the only thing that proves it. | Confirmed 2026-08-31 (a dashboard-publishing migration, mxcli v0.20.0). Script `09b` added two attributes with `alter entity … add attribute` and then defined two microflows. Re-running it after the attributes existed died on statement 1 with "attribute already exists" — and the two microflows at the end were never applied. It surfaced days later as `ACT_Version_Delete` quietly missing a call it had had an hour earlier, found by `DESCRIBE MICROFLOW` on a hunch; no gate saw it, because a microflow that no longer calls a sub-microflow is a perfectly valid model. Compounded by rule 21's defect one level up: six scripts held a grant on the same three entities, so whichever ran last decided their security. **The fix that makes both go away is the same one:** one owner per document, `create or modify` throughout, and a from-empty replay in CI or at wrap-up. Worked example incl. the before/after comparison: the project's `docs/REBUILD.md` pattern — 23/23 scripts replay, `BUILD SUCCEEDED`, rebuilt model identical to the live one element for element. |
| 23 | Name any document or entity that **might already exist** — `create or modify` on an entity, or any `create or replace` on a page, layout or microflow | **STOP → run `mxcli diff -p <app>.mpr <script>.mdl --format struct` FIRST.** It is read-only, it takes a second, and it prints exactly what the script would add and what it would REMOVE. Read the `-` lines before you exec, every time. Rules 21 and 22 tell you to write `create or modify` and to give each document one owner; this is the check that the name you chose is actually free. | Confirmed 2026-09-01 (a dashboard-publishing migration, mxcli v0.20.0). A new script declared `create or modify non-persistent entity DashboardPublishing."ViewerContext"` with one attribute, believing the name unused. The entity already existed, owned by an earlier page script, carrying four attributes — `VersionLabel`, `HasContent`, `Html`, `DashboardTitle` — which are the entire datasource of the app's viewing page. `diff --format struct` reported `+ Attribute SharedCount` and **four `- Attribute` lines**, i.e. `create or modify` on an entity does not merge into the attribute set, it **replaces** it. Renaming the new entity took ten seconds; the alternative was a page that renders nothing, on a model that would have passed `mx check` and mxbuild clean, since an entity losing four attributes is a perfectly valid model. **This is the cheapest guard in the file — the whole rule is `diff` before `exec`.** |
| 24 | Put a `DesignProperties: [...]` entry on a widget (Form orientation, Label width, Spacing, …) in an app scaffolded by `mxcli new` (any `--theme`) | **STOP → grep the theme first: `grep -l '<property name>' themesource/*/web/design-properties.json`. If it is not there, use the Atlas class instead (`Class: 'form-vertical'`, `spacing-outer-bottom-large`).** `mxcli new`'s theme layer ships a `design-properties.json` that does not carry Atlas's FormBase entries, so mxbuild rejects the property with CE6083 "not supported by your theme" — after `check --references` passed it. `design-spacing.md` says design properties and classes write the identical model; that holds only when the theme declares the property. | Greenfield pilot 2026-09-04, mxcli v0.20.0, Mendix 11.13.0, signal theme: `DesignProperties: ['Form orientation': 'Vertical']` on a DataView → exec ok, CE6083 at the gate, auto-restored. `Class: 'form-vertical'` built clean — and then changed nothing on screen, because in that theme the form layout is decided by the theme's own dataview rules, not the class (ui-loop.md "which side is wrong", row 1). The look caught it; no gate could. |
| 25 | Write a microflow with any loop, >20 planned activities, or a list built from a list | **STOP → run `microflow-preflight.md` and post its checklist first.** | Lint runs only after exec and counts only top-level activities (a loop body is invisible to CONV009/QUAL003); CONV011 commit-in-loop and MPR008 overlap findings came back on field builds after the write, not before. |

**Default to mxcli for:** entities/attributes/enums, associations (after SHOW ASSOCIATIONS check), microflows (without inline assoc-sets), demo users, module roles/grants, navigation.

## MDL gotchas (quick reference — common traps)

None of these needs a STOP, but each passes `mxcli check` and fails later — at native `mx check`, on SP open, or silently at runtime. The generated project `CLAUDE.md` already covers `EXTENDS` placement and the missing `CASE`/`TRY` statements; [[learned-microflow-patterns]] covers `toString()` on enums, `not(expr)`, and `empty` vs `''`. Only what lives nowhere else is kept here.

- **Quote / unquote retry rule:** when any identifier fails at `mxcli check`, `mx check`, or runtime, try the other form before concluding anything. Applies to every identifier position. One form always works; the other may parse and still write wrong BSON.
- **Never quote attribute names in path expressions:** `$Obj/Name`, never `$Obj/"Name"` — on `$currentUser` and every other variable alike. Quoted paths are valid MDL, so `mxcli check` passes; SP/`mx check` reject them with CE0117. Quotes belong on identifiers in *declarations*, and on an attribute in a path only when it collides with a reserved word.
- **Cross-module association paths need the entity name:** `$Item/ModA.Item_Other/ModB.OtherEntity/Attr`, not `$Item/ModA.Item_Other/Attr`. The short form compiles and SP rejects it (CE0117). A bare `= empty` check does not need the long form.
- **Keyword collisions:** widget, element and attribute names that match MDL/OQL reserved words (case-insensitive — `MIN`, `MAX`, `IN`, `OUT`, `COUNT`, `SUM`, `AVG`, `ROW`, `COLUMN`, `STATUS`, …) pass `mxcli check` and fail `mx check` (CE0161 in a `where` clause). Double-quote them or rename. Tell-tale: `DESCRIBE ENTITY` already quoting that one attribute in an access-rule list. Incident: `bug-logs/mxcli-bugs.md` → "Status / CE0161".
- **Enumeration values named with reserved words** (`Receive`, `Move`, `Count`, `Open`, …) cannot be targeted by `alter enumeration … modify value`, and quoting does not help in that grammar position. Use `create or modify enumeration` — which **replaces** the enum, so restate the full value set and the doc comment. Change captions only; renaming a value NAME silently breaks every reference and `mxcli check` will not say so.
- **Grants are co-located with the element, never deferred to one `security.mdl`:** `grant execute` ends the microflow script, `grant view` the page script, entity access the domain script — the entity and its access rule are one unit, same script, same commit. mxbuild raises no error for a missing grant; the only symptom is a blank screen or CE2729 once a non-admin role opens the page. A `roles.mdl` that only *creates* roles is fine. Pre-flight per entity: access rule in the same script? every module role that needs it granted? every module role composed into a user role? non-persistent DTOs — read/write only (CONV006)?
- **Module roles are module-scoped:** the role in any `GRANT` (entity, microflow, page) must be declared in the same module as the element — `ModuleA.Role` on a `ModuleB` element is a CE ("role not found in module"). Every module that owns grantable elements declares its own roles; user roles compose across modules: `create user role "AppUser" ("System"."User", "ModuleA"."ReadRole", "ModuleB"."ReadRole");`.
- **`System.User` in every user role:** without it users cannot log in, and nothing — mxbuild, SP, CE — says so.
- **Demo users:** name + roles only, no password block; never wipe, reset or re-create MxAdmin (ships with password `1`).
- **No `elseif` in page/widget expressions** (DynamicClasses, Visible, ContentParams, …): nest `else if … then … else …`. Microflow `IF/ELSEIF` compiles into decision splits; a page expression passes through to Mendix's parser, which has no `elseif` token → CE0117 at native `mx check`, invisible to `mxcli check --references` (2026-08-13; unquoting the paths did not fix it, only the rewrite did).
- **`DROP MODULE` removes the model only:** `themesource/<Module>/`, `skillssource/_modules/<module>/`, `javascriptsource/<module>/` stay as empty folders and every line of `theme/web/*.scss` survives, because that is app-level. See [[learned-stylegallery]] → "The Mendix DOM contract" before calling a reset total.
- **`mxcli check` does not catch corruption.** Every STOP row above is grammatically valid MDL that `check` passes; only mxbuild or SP open reveals the damage. Run the real mxbuild gate after every exec (`iterative-build-loop.md`).

## Final self-check (mandatory before reporting back)

After drafting a script, re-read it line by line against the table above — not just the mental pre-check you did before writing. Inline assoc-sets, conditional visibility inside datagrid customContent columns, and cross-module association traversals as widget datasources can creep in during drafting without intent. `mxcli check --references` will not catch them. This re-read is the actual corruption-prevention step.

**Then diff it before you exec it** (rule 23): `mxcli diff -p <app>.mpr <script>.mdl --format struct` is read-only and prints what the script would add *and remove*. The re-read above catches what you wrote; the diff catches what you did not know was already there — a name you believed free, an entity whose attribute set your `create or modify` would replace rather than extend. Read every `-` line.

**And check the size before you execute:** could you diagnose a failure of this script from the
error output alone, or would you be re-reading the whole file to find which unit broke? If the
latter, split it and say so in chat before executing — even when the build plan handed it to
you whole. A per-layer plan does not mean a layer is one script; see
`brd-to-build-plan.md` Step 3. Observed failure: a plan that put 13 microflows in one exec.

Isolate anything the other units depend on, group the rest by "would one failure explain the
others?", and do not over-split — every extra script is another approval prompt, and approval
fatigue hollows out RULE 1 as surely as an opaque mega-script does.
