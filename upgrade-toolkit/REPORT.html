The toolkit: approach, assets, learnings

our approach

The improvement loop

The toolkit is the product; the apps are its test bench. Each round runs real apps, collects what hurt, fixes it in the toolkit, proves the fix, then reruns the same apps.

Rules that keep it honest

  • Workers never edit the toolkit; they file feedback.
  • A fix needs a catch/pass control plus proof on real run data.
  • A gate is never weakened; unknown stays INVALID.
  • Only reviewed PRs reach main.
  • Success is the hand-work ledger, not a PASS.

Triage

Know what you are upgrading before you touch it.

  1. Exact versions and the path (which playbook)
  2. Module list; cross-linked modules go last
  3. Detect local edits in Marketplace modules
  4. Breaking changes, plus Emre's scanner if present
  5. Test inventory: roles, pages, endpoints
  6. Release impact: every relevant release-note row, classified
  7. Replacement map and Dojo report: deprecated parts still in use

2

Baseline

Record how the old app behaves, so there is something to compare.

  1. Seed realistic data, then freeze it
  2. Start the old app (Docker + Postgres)
  3. Data snapshot from a restart-neutral copy
  4. Mutant control: a planted change must FAIL
  5. A test login per role
  6. Smoke walk and journeys on the old app
seed_pg.pyseed_snapshot.pyrunapp.pysnapshot.pysmokewalk.js
3

Upgrade

Move one controlled step at a time, one commit per step.

  1. Update Marketplace modules through the batch runner
  2. Identity check after each module
  3. Convert with the target Studio Pro version
  4. Convert check: button mappings, warnings
  5. Update modules again for the new version
  6. Edited modules: keep, port, or replace
stepupdate.shmx10.sh convertconvertcheck.pyconvertmade.sh
4

Repair

Get back to zero errors, then a successful build and start.

  1. mx check, saved per attempt
  2. Match error codes to the repair table (14 rows)
  3. One fix per commit
  4. Check diff: worse → undo, cascade → keep
  5. Unknown error: diagnose and add a row
jardedupe.pyjarclash.pyscsscase.pymissing_deps.pycheckdiff.py
5

Gate

Prove the new app does what the old one did, on 10 rungs.

  1. New app on its own copy of the frozen data
  2. Run all 10 rungs with one command
  3. Review each difference: accept with a reason, or FAIL
  4. Write gate-summary.md with evidence paths
gate.sh --configdiff.pyshotdiffrun_journeys.py
6

Report

Make it something a customer can sign off.

  1. FAIL list with cause and owner
  2. INVALID list with what is needed to judge it
  3. Kept modules and accepted changes
  4. Compare against the publisher's own upgrade
  5. Toolkit feedback and hand-work ledger

Purchase Request 10.24 → 11.12.5, end to end

One app, driven through all six steps on the target LTS. Every problem became a toolkit fix or a recorded decision. The build passes, mx check shows 0 errors, and the visual diff caught the one break the compiler could not see.

Gate: not yet PASS. pipe-30 was INVALID: 79 of 146 journeys failed on the old app (gate: at most 43, 30%). pipe-33 is measuring nowThe failures come from the instrument, not the app. Since pipe-30, four fixes merged. PR-F36 archives each run's evidence before a rerun. PR-F37 fixes a landing check that a tab click hid (14 comment and attachment journeys). PR-F38 names the condition behind each button that is shown only in some states, so a reviewer can look the FAIL up instead of reading a screenshot; about 62 of the 91 pipe-30 failures have this shape. What went wrong, and what caught it

  • WorkflowCommons 4 removed the old comment API and possibly unmigrated data. Comments ported (D13); the data risk went to the user (D12, two releases).
  • Our tests, not the app, caused every remaining INVALID (F22–F25).

Who decided

  • 40 agent decisions, each with a written pass condition. A decision whose proof fails is reopened, not kept: D10 and D11 were reopened by the visual diff.

Why coverage is low

  1. No click path found. Most actions sit on pages opened by a NAV_ microflow, which the inventory did not follow. Fixed in PR #31 after most batch-4 runs had started. Re-measured on all 8 apps (8 Oct, last column): the reachable share is now 26–80%, against 0–29% covered. The gap between those two columns is cause 2, our test generator, not the apps.
  2. The test cannot walk the page. Tabs, pages that need a parameter object, Data Grid 2 rows, combo boxes, phone pages. Those journeys fail on the old app too, so they prove nothing (Quality Inspection: 117).
  3. No backend. Opcenter and Teamcenter pages stay blank on both sides.
  4. Dead pages. Pages nothing links to, e.g. unlinked admin pages. Until 12 Oct, not walked counted as not passed. Now (D18, F24) they are reported as unreachable: no user can open them before or after the upgrade, and mx check still compiles them. A page with a URL counts as reachable. Follow-up: list dead logic as removal candidates, since each dead module adds cost to the next upgrade.

Two conditional verdicts exist but no app has reached them yet: PASS (on stand-in APIs), when a backend was simulated, and PASS (except Teamcenter: N items), when only the listed steps that need Teamcenter were not checked. Both are rerun against the real systems before go-live.

Root cause found and fixed: menus that open pages through a microflow

These apps open their menu and home pages through NAV_ microflows, and the pages have no access rules of their own. Mendix allows that. The toolkit assumed every page needs its own access, so it found no click path to most actions, and journeys could only come out INVALID. Fixed in round 12 (internal fix, PR #31).

What can't move

Legacy core widgets

  • Most convert in a batch in Studio Pro 11.4+: Image, Combo box, Data Grid 2.
  • Template grid is converted by hand.
  • "ready" means the package declares pluginWidget="true". A widget built with pluggable-widget-tools older than 9.4.1 can still fail. Update the widgets and let Studio Pro's check decide.

where it stands

What the pipeline does well, and where people still come in

Runs without a person

  • Convert and build: version bump, mx check to 0 errors, MxBuild on the target LTS. Purchase Request 10.24 → 11.12.5 went end to end.
  • Predict before converting: the scanner matches the app against the brain's release facts. Every post-convert error is checked as predicted or missed.
  • Data safety: schema and id checks old vs new, and a ledger of every table, so data loss shows up as RED.
  • Screens: old vs new visual diff. On Purchase Request it caught the one break the compiler could not see (Atlas 3→4).
  • Real use: every action on every page is listed from the model, and click-through journeys are generated per role. They run on the old app first, then on the new one.
  • Honest gate: 1,218 controls, each with a known-bad and a known-good case. Unknown stays INVALID. There is no PASS on stand-in APIs.
  • Self-improving: every field defect becomes a toolkit fix with a control and proof on the real app. Purchase Request alone produced F13–F41.

Still needs a person

  • Confirm the user processes: scripts draft them from the model and the manual, and a key user confirms in about 15 minutes.
  • Screen review: 325 REVIEWs on Purchase Request, mostly expected Atlas 3→4 changes, judged one by one.
  • Judgment items: new module roles, behaviour changes, and whether to ship as two releases.
  • Test data: journeys need rows and open tasks to exist. Examples: an empty comment list, or no task waiting for the Approver. Today a person adds evidence or seeds the state.
  • Backends: Teamcenter and Opcenter need a vendor test system or recorded responses. They are exempt from the gate, with the reason named.
  • Environment: part of the container setup behind a proxy is still done by hand (backlog #18).
  • Click-through reliability: the main bottleneck right now. Most old-app failures were the instrument, not the app (pipe-30: 79 of 146; the limit is 43).

How we improve it next

  • Journeys under the limit: fix only the largest failure clusters, and label real test-data gaps as such. Hard stop: if the run after pipe-33 is still above 43, write up what is left instead of experimenting further.
  • Seed test data automatically: when a journey needs a row, make it first through the page's own create action (140 such needs on Purchase Request).
  • Structural check from MDL: dump the full app as MDL before and after, and diff them. This is cheaper and deterministic, and leans less on clicking (D47).
  • Less screen review: an Atlas 3→4 compat check that explains the expected deltas, so only real differences reach a person (#11).
  • Cost: reuse the old-app walk on reruns (#19); workers hand off after 2 gate rounds.
  • More apps: small Marketplace apps first, FSM last as the proof run.

Where we need others, including open source

  • Upgrade facts: breaking changes that the release notes miss. We hold 19 community leads at lower trust and need confirmations or counter-examples.
  • Widget successors: Dojo → React replacements. MxTreeTable, for example, has no React successor and blocks one app.
  • Test apps: public apps with realistic processes and data. We use public apps only, never customer data.
  • Browser patterns for Mendix widgets: PopupMenu, Data Grid 2, combo box and tab markup per version. Our engine changes are written up as an upstream proposal (research/journey-runner-verbs.patch.md).
  • Platform hooks: a stable, visible-only test id per widget. Today the same widget name repeats on hidden tabs, which caused F39 and F41.
  • Key users: 15 minutes per app to confirm the drafted processes.
  • How to contribute: a FEEDBACK.md row, or a PR with a control and a field run.
