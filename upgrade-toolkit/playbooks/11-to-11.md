# Playbook: Mendix 11.x to a newer 11.y

Field run: N1 (Opcenter EX Starter Kit 7.0.0, 11.6.3 to 11.15.0, one rung, about 50 minutes wall time;
`origin/runs/n1-opcenter-ef-11`). Steps refer to [steps/](../steps/). Items N1-n are rows in the N1 report
(TOOLKIT-FEEDBACK.md of that branch); this playbook is N1-14.

Route: ONE rung, no 10.24 rung, because the source already is Mendix 11. Mendix 11 converts from any 11.x. The rung is
still a full pass through steps 3 to 6 with its own verdict. What the N1 run needed, in order:

1. Module plan by "min Mendix", pre-convert pass on the SOURCE version.
2. Convert with the target toolset (N1: 12 s, 22 errors, all CE0463).
3. `mx update-widgets` (N1: 10 s, 22 CE0463 to 0 errors).
4. Post-convert module pass for the modules the source could not take.
5. Jar cleanup, SCSS case fix, build, quick start, gate.

## 1. Module plan by "min Mendix" (step 1 triage, step 3 upgrade)

Per module, take the newest version from `mxcli marketplace versions <content id>` whose minimum Mendix is not above
the version you are standing on, and put it in one of two plans:
- `plan1.txt`, the pre-convert pass: newest version with min Mendix at or below the SOURCE version (N1, on 11.6.3:
  CommunityCommons 11.5.1, DataWidgets 3.11.7, WebActions 2.11.2, NanoflowCommons 6.2.3, Atlas_Core 3.21.0).
- `plan2.txt`, the post-convert pass: the newest version with min Mendix at or below the TARGET, for the modules whose
  newest fit is above the source (N1: NanoflowCommons 7.4.0, min Mendix 11.12.3). A module with no version between the
  two needs only plan2 (upgrade.md 3).

Cross-module association targets go last in each plan, as everywhere (`idcheck.py --xmod`). Treat min Mendix as a hard limit
for plan1, not a hint (N1 held NanoflowCommons 7.4.0, min 11.12.3, for the post-convert pass).
As on the other rungs, "min Mendix" does not mean the package imports (a label that is not published, a package made
before 9.18): stepupdate takes the `--no-baseline` retry and logs it (N1: CommunityCommons).

Triage differences on an 11 source (both seen in N1, both open in its report):
- The MPR of an 11.x Marketplace export carries no content ids, so `localedits.py` calls every module UNKNOWN until
  you pass `--cid Module=<id>` per module; find the ids with `mxcli marketplace search`, and check an ambiguous name
  (VendorDesignSystem: 112317 "UI Resources" vs 120575 "Vendor Design System") against the installed version (N1-1).
- `--mxcli-diff` can answer "version label not published" for versions that `marketplace versions` lists, so the
  microflow and page layer is never judged; then the module stays UNKNOWN at that layer, never "no edits" (N1-2).
  Use `--proxy Module=<nearest listed version>`.

## 2. The pre-convert pass is optional here, do it anyway

Below 10.24 the pre-convert pass is REQUIRED (SKILL rules). On an 11 source it is not: nothing needs a 10.24 rung.
Still run it. It makes the "step: <Module>" commits that let `convertmade.sh` prove a module pristine after the
convert; N1 needed that for NanoflowCommons 7.4.0 (post-convert update, 1 committed, 0 kept). If you skip it, pass the
pre-convert report instead: `stepupdate.sh ... --localedits $W/localedits.json`, made WITH `--mxcli-diff`
(upgrade.md 3). A module with a RED local edit stays at its version and is reported (N1: Administration 4.3.2 kept).

## 3. Convert

`UPG_ROOT=<run> $B/heavy-lock.sh convert ... mx convert --in-place <abs app dir> 2>&1 | tee $W/convert-<ver>.log`
with the TARGET toolset (upgrade.md 2), then `python3 $B/convertcheck.py $W/convert-<ver>.log app/ --target <full ver>
--json $W/convert-<ver>.json`. CONVERTED with a backlog is normal (N1: 22 CE0463, all "widget definition changed").
NOT CONVERTED is a stop. Commit as "convert ...". Record the warning and deprecation counts too (section 7).

## 4. Widgets

`mx update-widgets` on the converted project (repair.md row 5), then `mx check` again: N1 went from 22 CE0463 to 0.
Do it before any other CE0463 work. A widget that stays red after update-widgets is a missing package or a version
the target does not accept: `repair/missing_deps.py` ([widgets](widgets.md) for the runtime breakers).

## 5. Jars and theme: automatic, but check the log

- Jars: `stepupdate.sh` runs `repair/jardedupe.py --apply` itself when its module updates finish (log
  `.stepupdate/jardedupe.log`, commit `jar:`; it covers userlib against vendorlib and older duplicates inside
  vendorlib, N1-6). Rerun it by hand after any later module change, then `repair/jarclash.py` for copies inside
  other jars (N1: pdfbox 2.0.24 in userlib against pdfbox-io 3.0.7 failed javac in CommunityCommons Misc.java:643
  until the cleanup ran; the pre-existing j2objc-annotations 1.3 against vendorlib 3.0.0 was there before the upgrade).
- Theme: repair.md row 11 (`repair/scsscase.py app/ --check`, then apply) before the first mxbuild on Linux. N1 hit
  the publisher's `commandBar` against folder `commandbar` import on both the old and the new build.

## 6. Gate

[steps/gate.md](../steps/gate.md), all rungs. Baseline (step 2) runs on the SOURCE toolset: Java 21 for every 11.x,
so there is no image choice to make. If `bin/gate.sh` exists in your checkout it drives these rungs; gate.md stays
the definition of what each rung proves. N1 environment limits that are not toolkit defects and must stay INVALID:
a home page that renders blank on both sides without the backing system, and journeys that need it.

## 7. Warning and deprecation counts for COMPARE (N1-11)

`mx check` prints errors only, so the warning and deprecation counts of a rung exist in two places only:
- the convert log: `convertcheck.py --json` (section 3) stores `errors`, `warnings` and `deprecations`;
- `mx check -w -d app/<app>.mpr` (the form T2 used for its comparisons), which ends with the same "The project
  contains N errors, W warnings and D deprecations." line.
Record both per rung in `$W/counts.md`: rung, source, target, convert-log counts, and the `mx check -w -d` counts after
repair (step 4 done). COMPARE against a publisher's or reference tree uses the same command on both trees, never the
convert log of one against the check output of the other. N1 numbers for orientation, not as a limit: 94 warnings and
40 deprecations in the convert log of the 11.6.3 to 11.15.0 rung.

## 8. What still applies from the 10-to-11 playbook

[10-to-11](10-to-11.md) "Blockers to expect" and "Behaviour changes" are about the Mendix 11 platform. For a source
below 11.6 the React 19 rows apply on the way up (legacy Charts `com.mendix.widget.custom.*`: blocker row 8, from 11.6);
from 11.6 up they are already in the source and the old app shows them. Do the hand check anyway, it is short (N1: no
legacy Charts, no own Java action, so none applied). Never read a pass on the publisher's NanoflowCommons as proof: see
[publisher-lessons](publisher-lessons.md) section 7 (N1-12: the CE4271 of NanoflowCommons 6.2.1 on 11.15 did not reproduce).

Not proved: more than one 11.x to 11.y rung (N1 is the only field run), a source below 11.6, and a target other than
11.15.0.
