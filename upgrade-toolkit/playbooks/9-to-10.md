# Playbook: Mendix 9.x to 10.24

Field runs: E5 and E5b (an app on 9.24.32 to 10.24.9). Steps refer to [steps/](../steps/).

Route: 9.x must be on 9.24 first, then convert to 10.24, then update modules ONCE on 10.24.
- mx 9.24 has no `module-import` verb, so `marketplace update` fails on 9.24 after the download (E5 F12). Do not try
  to update modules before the convert; convert first, then one update per module to its 10.24 version.
- Packages made before 9.18 fail the baseline import on 10.x ("open it in 9.18 to 9.24 first"), and the only way
  on is `--no-baseline`, which discards local edits without naming them (E5 F13). So run `localedits.py` (with
  `--cid` / `--proxy` where it says UNKNOWN) BEFORE the update, and treat every RED or LOGIC line by the
  [edited-modules](edited-modules.md) playbook first. stepupdate.sh takes the `--no-baseline` retry itself and logs
  it in `.stepupdate/no-baseline.txt` (E5b-26, E5b-27); a TARGET package made before 9.18 is SKIPped and kept (E4-16).
- No module can have a pristine "step:" commit before the convert on this path, so the convert's own rewrites
  (`@curve` geometry, Java action parameter metadata, managed JAR_DEPENDENCY rows, a widget app id) read as local
  edits. Run the post-convert updates with `stepupdate.sh ... --localedits $W/localedits.json` (the pre-convert
  report): a module that report shows clean (domain unchanged, 0 UI, 0 logic lines, and 0 modified elements: the triage
  localedits must run with `--mxcli-diff` before the convert, the offline layers compare no contents; on a 9.x source
  mx has no module-import, so that run is UNKNOWN for every module and the post-convert run on 10.24 is the proof,
  SKILL.md, NR1-4), with only convert/step/build/jar
  commits since the "original" commit, is CONVERT-MADE and forced (T1-15, T3-10, T4-3, T8-12). Commit the app's
  first commit as "original" and the convert as "convert ...".
- Coverage gap of localedits on 9.24 (E5b-7): pages and layouts are compared only when both models can be read by
  the same mxcli; a 9.24 app against a 10.x package often cannot. Run localedits again right after the convert, on
  10.24, before the post-convert updates: that run sees the page, layout and logic layers.
- CE2513 "Java 11 is not supported" right after the convert: the project setting JavaVersion is still Java11
  (E5b-16). `alter settings model JavaVersion = 'Java21'` (repair row 0).
- Tools: 9.24 runs on Java 11 (runapp.py picks the image by major: 9 to temurin 11), mx through `bin/mx9.sh`; 10.24
  on Java 21 through `bin/mx10.sh`. `mxversion.py` must agree with the toolset (host mxcli once picked a wrong mx; F7).

Known breaking items on this rung (scancover reports NO COVERAGE for 9 to 10, so these are the manual checks):
- Page call mappings (T2-1, found by a failed create-save journey only): `mx convert` makes implicit call arguments
  explicit, and inside a data view whose source is a microflow, nanoflow or association it can bind a Save button's
  argument to the PAGE PARAMETER (a different, empty object; 9.x meant the data view's object). mx check, build, start,
  data diff and smoke walk stay green. `convertcheck.py --mappings <pre-convert app> app/` lists every site whose
  mappings went from empty to explicit and marks the data-view ones REVIEW (exit 1); fix each, re-run to 0. The Opcenter
  run had 9 sites, 1 real. Keep the pre-convert app dir for it. A call to a flow in a protected add-on keeps an EMPTY
  mapping (convert cannot read the flow): CE1571, and `mxcli alter page` cannot set it; steps/repair.md row 12
  (`repair/copy_mappings.py`, T2R3-7).
- REST docs: 9.24 publishes `/rest-doc/<svc>/swagger.json`, 10.24 `openapi.json`. snapshot.py discovers both and
  diff.py compares the contract; the new openapi.json endpoint is NEW_ENDPOINT, allow it with a reason
  (`http./rest-doc/*/openapi.json # 10.x serves OpenAPI 3`).
- Java actions: assigning to a parameter is a javac error on 10 (final parameters). `javafinal.py app/` finds them;
  the fix (copy into a local) is by hand (E5b-30, open).
- Atlas 3.12 to 3.13+: compound Spacing replaces the four spacing properties; with an internal design system a blind
  `fix design-properties` gave 142 CE6085 (F16, again in E7). Cause: the internal design system maps whole properties
  to old names ("Margin top" <- "Spacing top"), which shadows Atlas's value-level oldNames. Fixer:
  `repair/design_props_guard.sh <app> <ver> --fixed CE6087 -- $B/repair/pds_oldnames.sh <ver> APP` (hides those
  property-level oldNames for the rename, restores the file byte for byte, E7-5). Fallback is Atlas 3.12.6 plus
  mapping the compound values back. That mapping is manual: CE6083 on vendor pages, no tool yet (E5b-29, open).
- Jars: updated modules move their jars to vendorlib and leave the old userlib ones (PDFBox 2, MendixSSO; F18).
  `repair/jardedupe.py --apply` straight after `mx sync-java-dependencies`, before the first build (E6-19: PDFBox 2 in
  userlib shadowed PDFBox 3 in vendorlib and javac failed). test_inventory.py lists duplicates that were there before
  the upgrade (E5b-4). An UNMATCHED line is a userlib jar of a module whose other jars moved, with no copy in vendorlib:
  usually a renamed or split artifact (netty 4.2 split netty-codec, NS-3); decide by hand. Then run
  `repair/jarclash.py app/` on 9 to 10 too, not only on 10 to 11: the move to vendorlib happens here.
- Convert with the TARGET toolset: `$B/heavy-lock.sh convert $B/mx10.sh 10.24.<n> mx convert --in-place <abs app dir>`;
  a 9.24 mx cannot convert to 10.24 (E7-11).
- Data diff rows every 9 to 10 run shows (E7-7), accept them with these reasons once you have checked them:
  `db.attr.System.User.Password` and `db.attr.System.User.changedDate` of the local admin (runapp.py sets its password
  on each start), `db.attr.System.FileDocument.Size` (9.24 writes 0 for a document without contents, 10.24 keeps -1),
  `db.entity.System.DataBrokerEntityMetadata` (removed by the platform, 0 rows).
- Screens: the 10.x Data grid 2 shows paging text ("1 to 4 of 4") and a taller header, so every grid page is a
  shotdiff REVIEW (E7-14). Open each pair; when only the paging line and header height differ, accept it per pair:
  `shots-*/<page>-* @sha256:<hash on the pair's line> # 10.x data grid paging text and header height, rows and
  columns identical`. The accepted change is ONE paging caption ("1 to 4 of 4"). A grid that shows two paging texts
  ("Currently showing 0 to 0 of 0" and "0 to 0 of 0"), or a filter caption that changed ("Status" became "Select"),
  is a styling clash with a kept design system or a lost widget setting, not a new caption: shotdiff reports it as
  `visible text changed` whatever the pixel share, so never accept it; fix it (repair.md row 19, NR1-25, NR1-37).
  An empty 10.6 Data grid 2 keeps its progress bar: settle.js saves that shot as `-STUCK`, which
  is closed the same way after a look (T7-22).
- Constants: a module update resets constants to package defaults and can add new switches; constcheck at the gate
  (an ADDED boolean is REVIEW), and shotdiff on the screens (the empty-chart case of E4 and E5b).

Widgets (batch 1, T3, T5, T8; details in [widgets](widgets.md)):
- Atlas_Web_Content 3.6.1+ overwrites `widgets/Charts.mpk` with Charts 6.x; pages with the legacy
  `com.mendix.widget.custom.*` charts then give CE0462 and missing_deps finds no package. Replace them with Charts 6
  (T3, `alter page ... replace ... pluggablewidget 'com.mendix.widget.web.barchart.BarChart'`). Restoring the old
  package as `ChartsLegacy.mpk` (T5) works on 10.x only: report it, it breaks from Mendix 11.6.
- Smoke walk console errors "attempt to uninitialize widget that is not loaded yet" plus React error #409 on pages
  that render the same (T8, 7 regressions from 3 sources): React widgets inside classic containers (10.0 widget
  wrapper) torn down before they loaded. Attribute each error to the page it names before counting regressions
  (T8-20), then pin the widget (widgets.md section 2). Deprecated Microflow Timer -> Events widget.

Not proved: the 9.24 app start on Java 11 in the controls (the runapp image choice is tested, the start is not).
