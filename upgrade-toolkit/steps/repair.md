# Step 4: repair (make it build and start)

A headless module update leaves the app unbuildable in predictable ways (E1 17: 126 errors; E5 F14 to F18). Work the
list in this order, one commit per fix, `mx check` (`$B/mx10.sh <ver> mx check app/<app>.mpr`, under the heavy lock)
after each, saved as `$W/check-<n>.log`: `$B/heavy-lock.sh check $B/mx10.sh <ver> mx check app/<app>.mpr > $W/check-<n>.log`.
heavy-lock.sh always takes a label first; it refuses an executable path in that place ("label missing", E6-14). After each fix: `python3 $B/checkdiff.py $W/check-<n-1>.log $W/check-<n>.log --fixed <codes the fix was for>`.
WORSE (more errors, or a new error code) means undo that fix. CASCADE (exit 0) means every code the fix was for is
gone and the rise comes from other codes that the old errors hid (E4: 121 CE1613 gone, 217 CE0463 revealed, E4-26):
keep the fix and continue with the new class. Without `--fixed` a rise is always WORSE.

mxcli v0.28.0 (#1408, #1474), what it changes for the rows above:
- `mxcli exec` is all-or-nothing. A script whose statement N fails now changes NOTHING and exits non-zero; before, statements 1 to N-1
  had landed. So after a failed `exec` (a replay script, an `exec` run through `alter_guard.py`, which then reports exit 3 "the command
  failed") the model is exactly as it was: fix the failing statement and rerun the WHOLE script. Do not run "the rest" by hand and do not
  `git checkout` as if it were half applied. alter_guard's own verdicts are unchanged and still needed: exit 0 with an unchanged unit is
  still NO-OP (the add-on case of row 12), because "all" does not mean "something was written".
- No `<Module>.User` role is created with a new module any more. Role grants must be explicit: `alter user role <Role> add module roles
  (<Module>.<ModuleRole>)` (row 8), and a replay that creates a module also creates the module roles it names (`create module role`) before
  any grant refers to them. Checked in this toolkit: no script or step emits `create module`, and row 8 and rolecheck.py already
  grant by name, so nothing relied on the automatic role; a hand-written replay for a module the project owns must not either.
- One mxcli version per run: the pipeline records it at triage (`work/state/mxcli-version`) and REFUSES (exit 3) a step run with another
  (`bin/mxcli_pin.sh`). DESCRIBE output differs between versions (widgets gain `readOnlyStyle`, microflow anchors are written in
  full, context comments are qualified), so a localedits report, a catalog or a replay script made with one version reads as edits against
  the other. alter_guard (before and after of one command) and `localedits.py --mxcli-diff` (both sides described in one call)
  compare inside a single invocation and cannot straddle versions; `convertmade.sh` (trusts the triage localedits.json), the triage

Hand repairs are labelled (change ledger, `bin/changelog.py` -> `$W/CHANGES.md`): every commit you or the agent make in app/ by hand goes through
`bash $B/appcommit.sh --app app --by agent|person --kind repair --rule repair-row-<N> --why "what and why, one line" -- <path> [<path> ...]`
(kinds: module-update, convert, repair, replay, theme, data, config; rule = the row above or `decision S-n`). It commits the named paths only and
refuses `-A`, `.` and an empty path list. The toolkit's scripts add the same two trailers (`Changed-By: toolkit`, `Upgrade-Change: <kind> <rule>`)
themselves, and `Upgrade-Step: S-n` too when the run has step records. Add `--step S-n --work $W` to `appcommit.sh` for every hand repair: the step is the repair item on the plan, or the one you opened for a decision of your own (steps/decide.md, Mid-run decisions). `bin/changelog.py` hands the commit to that step (`steps.py done`) and lists a commit without a step as "no step". A bare `git commit` still works, but the commit is listed in CHANGES.md as "unlabelled" and the gate summary asks for a decision about it.
